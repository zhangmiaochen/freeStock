# 按股票日线缓存：为什么「第一次打开 K 线」很慢，以及怎么解决

## 0. 一句话

`daily_bars` 是**按交易日分区**的（本机 2614 个文件、每个约 8KB、合计仅 20MB），
而"单只股票的全历史"查询原本会**打开每一个分区**再按代码过滤（3.97s）；
走"全市场批量缓存"那条路更糟 —— 为了 1396 行把 726 万行灌进内存（11.9s / 堆 1.5GB）。

**慢的不是数据量，是"一天一个文件"带来的固定开销。** 解决办法是把同一份数据
重排成"一个文件 = 一只股票"的**派生缓存**（落盘，约 25MB），
之后任意股票首开 ~15ms，不再占常驻内存，重启也不退化。

---

## 1. 实测：改前（`FREESTOCK_KLINE_PERF=1` 探针，见 §6）

| 场景 | 耗时 | 堆 |
| --- | --- | --- |
| `daily_bars` 分区数 | 2614 个文件 / 约 20MB | — |
| 只读一只股票的全历史（逐分区按代码过滤） | **3.97s** | 165MB |
| **冷启动第一次打开 K 线**（走全市场批量缓存） | **11.9s** | **1535MB** |
| 之后同一只 | 14ms | 1553MB |
| 之后换任意一只 | 11ms | 1608MB |
| 进程重启 | 又要重新灌一遍 | — |

两个附带结论：

* 那 11.9s 里有约 8s 是在给**全市场**组装 `bulkScored`（评分用的 `score.Bar`）——
  K 线从头到尾用不到它；
* 1.5GB 是**常驻**的：只要打开过一次 K 线，进程就一直扛着整个市场。

## 2. 根因：K 线走错了取数路线

`GetKline(code, adjust, 1990)` → `quoteRange` → `barsFor`：

```
barsFor(code, start, end)
  ├─ cachedBars(...)                 // 命中"全市场批量缓存"就直接返回
  ├─ bulkFillAllowed(start, end)     // ⚠ 只判断"缓存有没有覆盖 + 区间里有没有日分区"
  │    └─ fillBulk(19900101, today)  //    → 把**全市场 × 全历史**读进内存
  └─ lake.DailyBars(code, year, year) // 兜底：逐分区按代码过滤（1.75s/年）
```

`bulkFillAllowed` 的注释写得很清楚："不再按区间长度拒绝"。这对
**回填 / 评分 / 筛选 / 回测**是对的（它们的形态是"一批代码 × 一段区间"，
批量读一年只要 1.2 秒，逐只读要 546ms/只）。但 K 线是**"一只股票 × 全历史"**，
正好是这条路的反面：一次打开就把全市场灌进来，为了 1396 行。

（改后的路线是 `GetKline → Provider.KlineHistory`，为什么不能直接改 `DailyHistory` 见 §5。）

## 3. 方案：`symbol-major` 派生缓存

新代码：`internal/cnlake/symbolbars.go`（缓存本体，纯读写 + 构建），
`internal/service/provider.go`（接入），`internal/service/stock.go`（缓存目录装配）。

### 3.1 位置与布局

```
<config.json 同级>/cache/bars-by-symbol/<数据湖目录名>-<根路径指纹>/
    manifest.json              清单：版本 / 湖根 / K 线水位 / 分区水位 / 源指纹 / 股票数 / 行数
    bars/600519.parquet        一只股票的全部日线（按日期升序）
    bars/000001.parquet
    ...
```

* 放在**配置目录**（与 `portfolio.db` 同级）而不是写进用户的数据湖：
  它是 freeStock 自己的缓存，随时可以删，也不去动 cne 的产物；
* 目录名带一个根路径指纹：换数据湖不会串味；
* `bars/` 是**只读**的，写只发生在重建。

### 3.2 构建：分桶两阶段，内存有界

一次重建要按代码重排 726 万行。直接"全读进来再分组"峰值是 1GB 级
（`map[string][]BarRow` 会把行再复制一份），所以改成：

1. **分桶**：按代码哈希把行写进 32 个临时 parquet（内存里只有正在写的那点行）；
2. **逐桶排序 + 落盘**：每个桶读回来（本机约 20MB），按 `(代码, 日期)` 排序，
   再按代码切成最终文件。

实测：**29~31s**，峰值堆 **~130MB**（对比批量缓存 1.5GB）。全程后台跑。

### 3.3 读取：冻结历史用缓存，其余现读

```
KlineHistory(code, start, end)
  ├─ EnsureSymbolBars()                  // 非阻塞：不可信/没跟上就挂一次后台重建
  ├─ symbolCacheState()                  // 重算源分区指纹：不一致 → 不信任缓存
  ├─ symbolBarsFromCache(manifest, ...)  // <= 水位 用缓存；> 水位 现读日分区
  └─ 兜底：DailyBarsInRange([code], start, end)   // 缓存不能用时 4s
```

`symbolBarsFor` 返回的是**整条序列**（与批量缓存命中时的语义一致），
上层照旧按 `[start, end]` 过滤 —— 两条路线的组装共用 `assembleQuotes`，
估值 / 股本 / 前收 / 排序只要有一处不同，K 线就会随"缓存建没建好"而变。

批量问"哪些代码有历史"走 `SymbolBarsCache.Codes()`：读一次 `bars/` 目录
建成集合，按构建水位缓存在内存里（别逐个 `Has` —— 两千多次 `stat` 在
Windows 上是秒级，实测 1.2s vs 2ms）。

### 3.4 怎么保证"缓存里的数据永远是最新的"

三道闸，缺一不可：

1. **水位之后一律现读，不经过缓存。**
   `manifest.LatestDate` 是"缓存里**实际写到**的最后一根 K 线的日期"（不是分区名日期），
   查询时这个日期之后的部分直接读日分区 —— 新交易日、盘中追加、当天被重算，
   立刻可见，完全不用等重建。
2. **读之前校验源分区指纹。**
   清单里存着构建时那段"冻结历史"的 `(路径, 大小, mtime)` 哈希
   （`SourceSignature`）；每次读取前重算一遍，不一致就说明源头被改写过
   （补跑历史 / 重算某天 / 删了重写），这次**不信任缓存**、直接读源头，同时挂后台重建。
   代价实测：2614 个分区文件，冷启动首次约 238ms、之后约 20~45ms
   —— K 线首开因此从 25ms 变成 ~70ms，换来"复制品不可能被当成源头用"。
3. **数据更新一结束就失效。**
   cne 任务结束时 Runner 回调 `Options.OnFinish` → `CneUpdateService.SetOnDataChanged`
   → `StockService.InvalidateDerivedCaches` → `InvalidateSymbolBars`：
   应用自己触发的更新是**零延迟**失效，不必等下一次查询去发现。
   更新失败/被取消也照样失效（可能已经落了一半数据）。

两条安全边界：

* 指纹**在开始读数据之前**算好并写进清单。算在之后会有一个致命错位：
  构建期间被改写的文件会被记成"新指纹"，而缓存里存的还是旧内容 ——
  那就正好把"不一致"记成了"一致"。
* 重建**限流**（两次之间至少 2 分钟）+ 失败退避（10 分钟）。
  数据湖盘中是边写边变的，没有限流会退化成一直重建；限流期间查询走直读（慢但对）。

于是：

| 数据 | 来源 | 什么时候能看见 |
| --- | --- | --- |
| 水位之后（新交易日 / 盘中追加 / 当天重算） | 直读日分区 | **立刻** |
| 已缓存的历史被改写（应用内更新触发） | 直读 + 后台重建 | **立刻**（更新结束即失效） |
| 已缓存的历史被外部改写 | 直读 + 后台重建 | 下一次查询（校验指纹时发现） |

缓存始终只是加速层：**任何一条数据要么本来就来自源头，要么被证明与源头一致**。

### 3.5 并发与原子替换

* **进程内**：同一个缓存目录只允许一个重建在跑（`AcquireBuild/ReleaseBuild`）。
  一个进程里可能有多个 provider（切换数据源、测试里每个用例一个服务），
  没有这道闸会同时开跑几个 29 秒的重建、一起写同一个 staging；
* **跨进程**：staging 与 old 目录都带 pid（`.building-<pid>` / `.old-<pid>`），
  两个 freeStock 同时重建也不会互相踩；
* **原子替换**：新内容全部写完后整体换名，读者任何时候看到的都是
  "完整且与 manifest 一致"的一份；Windows 上换名可能因为读者握着文件句柄而失败，
  所以带重试，失败也不会把旧缓存弄丢。

## 4. 实测：改后

| 场景 | 改前 | 改后 |
| --- | --- | --- |
| K 线首开（缓存没就绪） | 11.9s / 堆 1.5GB | **4~5s / 堆约 130MB** |
| K 线首开（缓存就绪，含指纹校验） | 12ms（但重启要重新灌 11.9s） | **~70ms**（其中指纹 20~45ms） |
| 打开 000001（股票与指数同名的裸码） | 0.5~6s（全市场 120 天批量灌入） | **~70ms**（走同一份缓存） |
| 一次构建（后台，数据更新后一次） | — | 29~31s / 堆约 130MB / 磁盘约 25MB |
| 股票列表"不限起点补抓" | **3.49s**（全表扫描） | **24ms** |

最后一行是顺带收益，也是差距最大的一处：那一步要回答"2242 个没有近期行情的代码，
历史最后一根 K 线是什么"，原来从 1990 年开始扫全部分区。缓存里
**没有文件的代码 = 整段历史都没有 K 线**，而"哪些代码有文件"读一次目录就能
建成集合（本机 5821 个文件，几十毫秒，按构建水位缓存在内存里），
于是 2242 个代码全都在集合外，一个文件都不用打开。

（数字来自 `FREESTOCK_KLINE_PERF=1` 探针；`no-cache` 那一行两次跑分别是
3.97s / 5.28s，差异来自文件系统缓存冷热，不是实现变化。）

## 5. 影响面：哪些没变，为什么

* `DailyHistory`（回填 / 评分 / 筛选 / 回测 / 计划）**一点没动**，仍然走批量缓存 ——
  它那些调用方都是"一批代码 × 一段区间"，改道会让它们从 1.2s/年
  变成 546ms/只（全市场几小时）；
* K 线单独走新方法 `Provider.KlineHistory`（`kline.go` 里只有一处调用）；
* 单只股票的**点查询**（`QuotePoint`：K 线页判断裸码是股票还是指数、财务页取最新价）
  也优先走这份缓存。原来它会触发"全市场 × 120 天"的批量灌入（实测 0.5~6 秒），
  而调用方只是想知道"这只票最后收在哪"。**批量流程不受影响** ——
  `stockdbProvider` 那边还是原来的键查询；
* free-stockdb 那条路完全不受影响（`KlineHistory` / `QuotePoint` 就是原来的键查询）。

## 6. 运维与复测

* **删缓存**：删掉 `<config.json 同级>/cache/bars-by-symbol/` 整个目录即可，
  之后第一次查询退化成直读，随后自动重建；
* **看是否生效**：日志里会出现

  ```
  INFO 按股票日线缓存就绪 symbols=5821 rows=7268708 latest=20261012 sourceThrough=20261012 sourceFiles=2614 elapsed=29.6s
  ```

  失败只会打一条 `WARN 按股票日线缓存重建失败（查询会退回直读）` —— 界面照常可用；
* **强制刷新**：正常情况下不需要 —— 源头一变指纹就不一致，缓存立刻不再被信任；
  应用内的数据更新结束还会主动失效。真要手工来一次就删目录；
* **性能探针**（会真建一次缓存，放在临时目录里）：

  ```powershell
  $env:FREESTOCK_KLINE_PERF='1'
  go test ./internal/service/ -run TestKlinePerfProbe -v -count=1 -timeout 30m
  ```

  它会打出 `PROBE sourceSignature ... elapsed=...`（每次查询都要付的那笔钱）、
  缓存命中/未命中的 K 线耗时、以及补抓走缓存 vs 全表扫描的对比；
* **正确性用例**：
  * `internal/cnlake/symbolbars_test.go`：与直读逐行一致、水位/覆盖、幂等、
    构建闸门、代码索引、**源分区被重写时指纹必须变**；
  * `internal/service/kline_symbol_cache_test.go`：缓存 vs 直读逐字段一致、
    水位变旧时补尾不缺不重、没有缓存时退化可用、
    **源头被重写后 K 线必须看到新数据**（`TestKlineHistorySeesRewrittenSource`）。

## 7. 还能再快吗

* 每次查询的指纹校验（20~45ms 热、238ms 冷）是"永远最新"的代价。
  要再省掉它，需要更便宜的变化信号，例如基于
  `ReadDirectoryChangesW` 的文件系统监听（要引入平台相关代码或第三方依赖）；
  现在这个方案不牺牲正确性，所以先不做；
* 构建 29~31s 里大头是写 5821 个小文件（parquet footer/落盘）。
  可以按年合并成 `code-year` 粒度（文件数 ×10，单文件仍很小）；
* 缓存正文可以再省一层：文件是"一只股票一份"，行里的 `symbol` 列其实是冗余的；
* 若哪天 cne 侧直接产出 `derived/bars_by_symbol/`，freeStock 只需要读，
  这份缓存连同它的失效逻辑都可以删掉 —— 那是最干净的形态。
