# 存储迁移（核心库 / 分析库）操作说明

面向 NAS(Docker) 与 Windows 桌面。迁移是**手动操作**，程序不会自己搬数据。

## 1. 目标结构

```text
data/
  portfolio.db           旧单库（迁移的源，永远保留，回滚靠它）
  portfolio-core.db      核心库：portfolio / position / txn / shares / money
  analytics.db           分析库：stock_strength / market_state / signal_history
                         + 四张建议快照表
  migration-state.json   迁移状态（程序据此自动启用新库）
```

**回测三张表暂时留在 `portfolio.db`**：它们带 `portfolio_id` 外键指向核心组合表，
而分析库没有核心表；且回测结果目前仍由旧库读写。等独立回测库那一步再整体搬。
把回测表复制进分析库会导致两个后果：`FOREIGN KEY constraint failed (787)`，
以及"新回测只写旧库、分析库里是旧副本"的数据分叉。

## 2. 界面上怎么做

`设置 → 数据源 → 数据存储迁移 → 开始迁移`

- 迁移期间每 2 秒刷新一次状态，显示阶段、当前表、已处理行数：
  - `核心库复制`：5 张核心表，逐表提交，每张完成后才更新进度；
  - `核心库校验`：`PRAGMA quick_check`；
  - `分析库复制`：按 rowid 每批 1 万行，逐批提交（不做整表 COUNT 预扫）；
  - `分析库收尾（索引/完整性）`：重建索引 + 逐表 `quick_check`。
- 成功后 `migration-state.json` 记为 `succeeded`，程序**自动**切到新库，不需要环境变量。
- 同一状态再次点击不会重复迁移。

## 3. 失败/中断后怎么恢复

迁移是可重入的：

| 现场 | 新版本行为 |
| --- | --- |
| `portfolio-core.db` 已复制完、校验通过 | 直接复用，不再扫旧大库 |
| `portfolio-core.db` 是空的/坏的（源有组合、目标 0 个） | 改名成 `.stale-<时间戳>` 归档，重新复制 |
| `analytics.db` 已复制完但卡在收尾（状态 10/10） | **只做校验收尾**，不重新复制 |
| `analytics.db` 是半成品 | 改名归档，重新复制 |
| 上次状态停在 `core 5/5` | 复用核心库，直接进分析阶段 |

归档只是改名，不删除数据。界面上会显示归档了哪些文件。

## 4. 启用与回滚

- 启用：迁移成功后自动生效（重启后依然生效，因为状态在 `migration-state.json`）。
- 强制指定路径（可选，优先级最高）：
  ```yaml
  environment:
    FREESTOCK_PORTFOLIO_CORE_DB_PATH: /data/portfolio-core.db
    FREESTOCK_ANALYTICS_DB_PATH: /data/analytics.db
  ```
- 回滚：删掉/改名 `migration-state.json`，重启即回到 `portfolio.db`。
  **不要删 `portfolio.db`**，也不要删归档的 `.stale-*`（确认新库稳定后再清理）。

## 5. NAS 上的耗时预期

迁移耗时主要由**读旧库**决定。实测那台 NAS 顺序读约 7.9 MB/s，
4.9 GB 的旧库光读一遍就接近 10 分钟，加上写出与最后建索引，
整体到几十分钟是正常的；界面上的 `行已处理` 必须持续增长。

判断"是不是卡死"只看两点：

1. `migration-state.json` 的 `currentTable` / `rowsDone` 是否变化；
2. 容器日志是否有 `存储迁移：` 前缀的阶段切换。

## 6. 容器日志关键行

```text
存储迁移开始
存储迁移：发现已有核心目标，开始快速校验
存储迁移：核心目标校验通过，进入分析库
存储迁移：发现上次已复制完的分析库，改为只做校验收尾
存储迁移：直接接手完成（未重新复制）
存储迁移：已归档上次遗留的目标文件
```

## 7. 跨库引用与一致性保障（重要）

三个库是**三个独立文件**，SQLite 的外键级联**不跨文件**。所以下面这些点由应用层保证：

| 场景 | 处理 |
| --- | --- |
| 删除组合 | 核心库删组合（持仓/流水/资金靠库内外键级联）；同时按 `portfolio_id` 清理**旧库的回测记录**与**分析库的四张快照**。失败只记日志，不回滚删除。 |
| 回测取数 | 组合元数据取核心库；评分/市场状态/信号取分析库；回测结果三张表读写都在旧库。混用会直接改变回测结果（过期市场状态会改变牛熊闸门）。 |
| 生成建议 | 组合与持仓取核心库；评分/广度/市场状态/信号取分析库；快照写分析库。 |
| 信号概览 | 读分析库的 `signal_history`。 |
| 迁移后误删文件 | 状态说成功但核心库/分析库文件不存在时，**回退旧库并告警**，绝不静默新建空库（那会表现为"组合列表为空/评分全 0"）。显式 env 路径仍按用户配置执行。 |
| 并发访问 | 所有连接设置 `PRAGMA busy_timeout=15000`：迁移、回填、信号生成各用独立连接访问同一文件，默认 `busy_timeout=0` 会把正常等锁变成立刻 `SQLITE_BUSY`。 |
| 核心库 schema | 迁移后的核心库用 `OpenCore()`（core-only）打开。用完整 schema 打开会把空的评分/回测表建进核心库，把"表不存在"变成"表存在但永远为空"的静默错误。 |
| 分析库 schema | 新建的分析库只建 7 张分析表（`openAnalyticsOnly`），**不建核心表**。这样把查询发到错库会得到 `no such table`，而不是 0 行。早期版本建出来的 `analytics.db` 里可能残留空的 `portfolio` 等表，程序不会使用它们；迁移完成后可人工删除该文件让它按新 schema 重建。 |

## 8. 已知边界

- 回测三张表仍在旧库（见 §1）。
- 分析库的清理仍按时间窗口 `DELETE`（`FREESTOCK_SCORE_RETENTION_DAYS`），
  尚未做"按年分区文件淘汰"。
- 独立 Worker 进程、generation 快照发布尚未实现，回测/回填仍与页面同进程。
