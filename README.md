# FreeStock

用 **Wails3 + Vue 3 + shadcn-vue** 做的 A 股桌面工具，数据来自 [free-stockdb](https://github.com/zhangmiaochen/free-stockdb)。

当前已实现 **股票列表**（按市场 → 按行业分类）、**K 线图表**（日/周/月/年 + 均线/布林/MACD/资金流）、
**财务数据**（财报科目、股本结构、股东户数、十大股东）、**板块行情**、**市场温度**、
**条件选股**、**组合管理与回测**、**多期限性价比评估**（1/3/6/12/36 个月独立的估值与质量评分）。
界面采用「左侧菜单 + 右侧内容区」结构，后续功能按同一套约定增量添加即可。

行情来源可切换：**free-stockdb**（HTTP）或 **cnequity 本地数据湖**（直接读 parquet）；
财务数据则**始终**来自数据湖，与行情源无关。

### 2. 板块行情（`/boards`）

申万一级 / 二级 / 三级 / 概念四个分类，热力图 + 可排序表格 + 成分股展开。
行情有**两套周期口径**：**当日**（成分股当日行情聚合）与**区间**（最近 N 个交易日的涨跌幅，
可选 5/10/15/30/60 天或自定义，默认 5 天）。

#### 2.1 板块行情是「算出来」的

板块数据（`板块*` 表 / 数据湖的 `industry_members`）**只有成分名单，没有行情**。
所以板块行情必须由成分股行情聚合，这一步放在后端（`internal/service/board.go` 与 `board_period.go`），
因为口径属于领域逻辑，而且股票列表的行情在后端本来就有缓存。

**当日口径：**

| 指标 | 口径 | 为什么这么定 |
|---|---|---|
| 涨跌幅 | **流通市值加权** | 接近申万行业指数口径，避免小盘股几笔单子把板块拉偏 |
| 等权涨跌幅 | 成分股简单平均 | 和加权值对比能看出是**普涨**还是**少数权重股拉动** |
| 成交额 | 成分股求和 | 热度 |
| 换手率 | Σ成交额 ÷ Σ流通市值 × 100 | 板块层面不能简单平均个股换手率 |
| 涨/跌/平家数 | 按个股涨跌幅正负号 | 板块内部结构 |
| 领涨 / 领跌股 | 涨跌幅极值 | 定位龙头 |

> 加权与等权有时会给出**相反**的信号：小盘股涨 10%（市值 1 亿）、大盘股跌 1%（市值 99 亿）时，
> 加权是 −0.89%、等权是 +4.5%。两个都给就是为这种情况。

**区间口径**（`internal/service/board_period.go`）：

| 项 | 口径 |
|---|---|
| 区间涨跌幅 | 成分股**区间**涨跌幅的流通市值加权（同时给等权） |
| 区间起点 | 倒数第 `N+1` 个交易日作**基准日**，算到最新收盘 —— 即"最近 N 个交易日的涨跌" |
| 区间涨跌家数 | 按成分股**区间**涨跌幅的正负号 |
| 区间领涨/领跌 | 区间涨跌幅极值 |

三处**有意的近似**（界面里也写了出来，别当成 bug）：

1. 用**不复权收盘价**：除权除息日价格自然回落，会被算成下跌。要做复权得逐只取复权因子
   （全市场 5000+ 次请求），代价远大于收益。
2. 权重用**最新**流通市值，不是区间起点市值 —— 数据源不提供历史市值
   （数据湖的 `valuation_metrics` 只有最新一天）。
3. 成分名单只有**当前**这一份，区间内被剔除的股票仍按当前名单计算（与条件选股的已知限制一致）。

**算不出来 ≠ 涨跌幅是 0**：成分股在区间起点还没有行情的（次新股、长期停牌、未同步）**不参与**区间统计，
表格里显示「—」而不是 0% —— 按 0 摊进等权平均会系统性压低板块涨幅。
表格里的 `有区间行情/成分总数` 也是同一个道理。

> 没有**区间**成交额与换手率：那需要把区间内每一天的成交额都取回来，而 free-stockdb 的区间查询
> 会把每条记录的 21 个字段全返回（实测 106 个交易日 = 34KB/只、全市场 190MB、16 秒），
> 是"只取几个基准日收盘价"（点查询，7500 只 1 秒）的 4 倍以上。热度看当日成交额就够了。

#### 2.2 重叠分类必须区别对待

分类有两类，混在一起会给出错误的市场总量：

- **申万一级/二级/三级**：层级分类，每只股票每级只属于一个板块 → 可看成一次完整切分
- **概念**：多对多，一只股票同时属于多个概念 → 成分总数是标的数的 **10.6 倍**

所以后端会计算 `Overlapping` 与 `OverlapRatio`（成分总数 ÷ 标的数，> 1.2 判定为重叠）。
实测：申万各级 0.57~0.67（不重叠），概念 10.57（重叠）。

界面上**措辞会跟着变**：不重叠时显示「总成交额」，重叠时显示「成分成交额合计（有重叠）」
并明确写出「各板块成交额会重复计入，不是市场总成交额」。
否则概念页会显示 25.2 万亿，而真实市场总成交额是 1.4 万亿 —— 放大 18 倍。

> 涨跌幅不受重叠影响，因为每个板块各自加权。

| 区块 | 说明 |
|---|---|
| 分类切换 | 申万一级(28) / 二级(104) / 三级(227) / 概念(978)，带板块数 |
| 周期切换 | 5日 / 10日 / 15日 / 30日 / 60日 / 自定义（2~250 个交易日），默认 5 日 |

| 热力图 | 面积 = **当日**成交额（体量不随周期变化），颜色 = **所选周期**涨跌幅（红涨绿跌，色带 ±6% 封顶）。超过 80 个板块时按成交额取前 60 并标注 |
| 表格 | 「当日」一列 + 每个周期一列（默认高亮当前周期并按其降序），另有当日成交额/换手率/涨跌家数/领涨股；点表头可换排序，悬停任一区间单元格能看到该板块的等权、区间涨跌家数与区间领涨/领跌 |

这不是装饰 —— 没有它的话，用户会发现涨跌家数加起来对不上成分总数，却不知道原因
（停牌 / 退市 / 未同步）。

#### 2.4 性能

| 操作 | 耗时（本机 free-stockdb，5647 只成分股） |
|---|---|
| 当日行情首次聚合 | ~1s（含股票列表加载） |
| 首次算区间行情（5 个基准日） | ~8s（约 2.8 万次点查询），此后切分类/切周期不再取数 |
| 加一个**新**周期（如自定义 20 日） | ~1.5s（只补缺的那一个基准日） |
| 切分类 / 切周期（命中缓存） | 2~250ms |

缓存的是**历史基准日收盘价**（成交日一变就作废，6 小时过期），不是"算好的板块涨跌幅"，
所以切周期只是内存里重算。数据湖那条路更快：它按交易日分区，
`ClosesBefore` 一次扫完区间所有分区，实测 5 个基准日约 550ms
（详见 `docs/free-stockdb-api.md` 的性能实测与 `internal/service/provider.go` 的说明）。

**数据湖上"初始化慢"的那 4 秒在哪**（实测拆解，2026-10）：

| 阶段 | 耗时 | 说明 |
|---|---|---|
| 全量行情快照 | 4~6s | **瓶颈** |
| ↳ 其中：最近窗口读 | 0.7s | 120 个日分区 |
| ↳ 其中：**不限起点补抓** | **3.5~4s** | 把 `daily_bars` 的**每一个**日分区（本机 2614 个）的 7 列全解码，只为找 2479 个"最近没有行情"的代码的历史最后几根 K 线 |
| 板块区间基准价（5 个周期） | 0.55s | 一次扫完区间分区 |
| 板块聚合（1001 个概念板块 × 5 周期） | 0.2s | 纯内存 |

针对它的两处优化（**都不改变任何数据**，见 `internal/service/warmup.go` 与
`internal/service/provider.go` 的 `retryQuotes`）：

1. **补抓结果按交易日缓存**（6 小时）：它是历史 K 线，同一天里不会变。
   于是每 10 分钟重建一次全量列表（`universeTTL`）不再重扫 —— 实测
   "清缓存后再取"从 **4.6s 降到 1.05s**；
2. **启动时后台预热**全量快照与板块基准价：用户启动后一般先看别的页面，
   真正点进板块行情时通常已经好了。

那条 3.5~4s 的扫描**能不能省掉**也量过（`zz_retry_impact_test.go` 是决策记录）：
补抓回来的 237 个标的**全部是早已退市、不在任何板块成分里的老代码**，
去掉之后 **1265 个板块的数字一个都不差**（涨跌幅、成交额、涨跌家数、领涨股全同），
唯一变化的是"重叠倍数"这个**全市场**口径（概念 45.57 → 47.51 —— 分母里不再计入
237 个没有当期行情的标的）。**要不要用它换 4 秒是产品决定，目前保持原口径。**

顶部搜索，中间标的简要信息，下方多面板联动图表（ECharts）。
**股票与大盘指数共用这一个页面**（同一套搜索、周期、指标与图表）。

| 能力 | 说明 |

| 搜索联想 | 支持**代码 / 名称 / 拼音全拼 / 拼音首字母**（`600519`、`茅台`、`guizhou`、`gzmt` 都能搜到），带键盘上下选择 |

| 周期切换 | **日 / 周 / 月 / 年**，前端即时聚合（周线按 ISO 周，与官方 SDK 口径一致），无需重新取数 |

| **框选区间统计** | 一个开关打开后在图上**拖一个矩形**，统计这一段的区间涨跌幅、最高/最低、最大回撤、振幅、日均波动、涨跌天数与成交额（见 3.2） |
| 指标参数 | **布林线（周期 N / 倍数 K）与 MACD（快线 / 慢线 / 信号）参数可自定义**，带默认值按钮与合法性校验（慢线必须大于快线） |
| 图表 | 蜡烛 + 均线 + 布林 / 成交量 / MACD 三面板联动，十字光标、缩放条、悬浮明细 |

| 财务指标 | **ROE(TTM) / 每股收益 / 每股净资产 / 净利润TTM / 净资产**（由行情推导，见下节） |
| 资金流 | 信息栏显示**主力净流入（当日 / 5 日 / 20 日）**；图表上是一个独立的**资金流面板**（主力净流入柱 + 5 期均线，随周期自动求和） |
| 记忆 | 周期 / 复权 / 指标开关 / 指标参数 / 均线配置都写入**本地配置文件**，下次打开保持 |
| 交互 | 选中标的写入地址栏（`#/kline?code=600519`、`#/kline?code=000001.SH`），可刷新/前进后退还原 |

**指数与股票的区别**（都是数据本身决定的，页面上也写了出来）：

- 指数只有**价格与成交量**：没有 PE / PB / 市值 / 股本 / 换手率 / 资金流 / 板块归属，
  这些行整块隐藏（后端也不会编一个像模像样的数字）；
- 指数**没有复权**，三种复权方式给出完全一样的曲线；
- 指数行情只在数据湖的 `index_bars` 里（free-stockdb 没有指数表），
  按年分区，本机 8 个指数、2023-10-09 起 728 个交易日；
- 裸码解析：`399001`（深证成指）这类**不是股票**的裸码会按指数打开；
  `000001` 这种两边都有的**以股票优先**（要上证指数请带 `.SH` 后缀）。

#### 3.1 斐波那契黄金分割辅助线

一个开关（工具栏「斐波那契」）画出 7 条黄金分割位：**0 / 23.6 / 38.2 / 50 / 61.8 / 78.6 / 100%**，
其中 38.2 / 50 / 61.8 三档画得更亮（黄金档）。

**区间是动态的**：取**当前可见窗口**的最高价与最低价，分割位 = `高点 − 比例 × (高点 − 低点)`。
所以**缩放、平移之后分割位会跟着重算** —— 这正是"位置动态计算"的含义：
屏幕上关心的就是这一段的高低点，固定成某段历史反而对不上。

**两个方向**指的是同一个价位的两种读法，界面上直接标出来：

| 标注 | 含义 | 用法 |
|---|---|---|
| `↓ 61.8%` | 从**高点**回落的回撤比例（涨势回撤） | 该价位是**支撑**参考 |
| `↑ 38.2%` | 从**低点**反弹的比例（跌势反弹） | 该价位是**压力**参考 |

两者互为镜像（`↓23.6%` 与 `↑76.4%` 是同一个价位），所以**一条线标两个数**就够 ——
画两遍只会得到重叠的线。区间两端直接标「高点 / 低点」的价格。

实现上有两处刻意的选择（`frontend/src/lib/fibonacci.ts` + `components/kline/KlineChart.vue`）：

1. 缩放/平移时**不做整图重绘**，而是 `setOption({series:[{markLine}]}, {notMerge:false})`
   这条**局部更新**路径：整图重绘会重建 dataZoom（平移会被自己重置，甚至来回触发事件），
   还会闪一下并打断十字光标；
2. 纯计算部分（可见区间折算、分割位、方向判断）全在 `lib/fibonacci.ts` 里，
   不依赖 ECharts，可以单测覆盖（`tests/fibonacci.spec.ts`）。

开关状态与其他指标开关一样写入本地配置文件（`showFibonacci` / `showRangeSelect`）。

#### 3.2 框选区间统计

工具栏上一个开关（「框选统计」），开启后**在图上按住左键拖一个矩形**，
统计这一段区间的涨跌信息。区间由用户划定，**不随缩放变化** ——
这与斐波那契的"可见窗口"是两套不同的区间读法，所以两者**可以同时开**。

| 指标 | 口径 |
|---|---|
| 区间涨跌幅 | **(首根开盘价 → 末根收盘价)**，与行情软件「区间统计」同口径 |
| 区间最高 / 最低 | 区间内 `high` / `low` 的极值，给出出现日期与**距首开**的百分比 |
| 最大回撤 | 在**收盘价**序列上算，给出谷底日期 |
| 振幅 | `(区间最高 − 区间最低) ÷ 首根开盘价` |
| 日均波动 | 逐日涨跌幅的**均值绝对偏差**（**未年化**） |
| 上涨 / 下跌天数 | 按逐日涨跌幅的正负号数，平盘两边都不算 |
| 区间成交额 / 成交量 | 求和。**指数没有成交额**（数据源只给价格与成交量），此时整行隐藏 |
| 交易日数 / 自然日跨度 | 分开给：春节前后 10 个交易日可能横跨 25 个自然日 |

**为什么区间涨跌幅用"首根开盘"而不是"首根收盘"**（`lib/rangeStats.ts` 里也写了）：

- 用首根**收盘**：会漏掉这段行情自身的开盘跳空 —— 当天从 10 开到 11 收，
  却按 11 起算，等于把第一天的涨幅算丢了；
- 用**前一根**收盘：需要区间外的数据，而用户框的就是"这一段"，
  越出框外取值会让结果与框对不上。

**为什么最大回撤用收盘价而不是盘中最低价**：用盘中价会把"当天插针后收回"
也算成回撤，数字会明显虚高（README 的实测用例里差 4 个百分点）。
收盘价回撤才是持有者真实的资金曲线回撤。

**为什么日均波动是均值绝对偏差而不是年化标准差**：它要回答的是"平均每天动多少"，
年化标准差对散户读数字没有帮助，而且要先假设 250 个交易日、收益率独立同分布才成立。

实现上有几处刻意的选择：

1. ⚠ **光在 option 里写 `brush` 是没用的，必须显式调一次 `enableBrush`** ——
   而且**每次缩放（datazoom）之后还要再补一次**，见下面的专节；
2. **开启时禁用 inside 缩放（拖拽平移），滑条照旧可用** —— 框选与平移都用左键拖，
   不禁用就会"一边拉框一边把图拖走"，而且平移会连带触发斐波那契重算，
   框选过程中图一直在动。所以不是靠挡事件，而是让两者不抢同一个手势；
3. **区间端点直接取 brush 给的 `coordRange`**，不要自己换算、也不要按别的字段判断：
   `chart.convertFromPixel({xAxisIndex: 0}, [px, px])` **返回 null**（实测），
   而 `areas[0]` **只有** `range`（像素）与 `coordRange`（轴数据坐标），
   **没有 `x` / `y` / `width` / `height`**。
   并且 `coordRange` 的形状是 **`[[x0, x1], [y0, y1]]`** ——
   x 的两个端点都在 `[0]` 里，`[1]` 装的是 y（价格）。取错一项，
   区间就会被撑到数据末尾（见下面的专节）；
4. 松手后**清掉 brush 自己那层虚线框**，改用主图 series 的 `markArea` 画常驻高亮：
   brush 的选框横跨所有面板，而统计只统计 K 线，高亮也只该盖主图；
   `markArea` 必须设 `silent: true`，否则它会吃掉鼠标事件、挡住十字光标
   （与斐波那契的 `markLine` 同一个坑）。图表上还叠了一个
   `pointer-events: none` 的装饰层，只为把光标换成十字；
5. **双击取消框选**得自己接：ECharts 的 brush 默认 `removeOnClick: false`
   （源码注释写明"单击不清，因为用户可能随手点一下"），所以"点一下清掉"的
   直觉在这里并不成立；
6. **切周期 / 换复权 / 换标的都会清掉框选**：日线的"第 10~20 根"不是周线的
   "第 10~20 根"，留着旧下标只会给出与眼前图表对不上的数字；
7. **只框到一根时不显示统计面板**（单根不构成"区间涨跌"，那只是它自己的开盘到收盘）。

##### 六个只有真浏览器才测得出来的 ECharts 坑

这一块连着踩了六次，共同点是"配置看着没问题、单测全绿、但功能就是不工作"：

**① 光写 `option.brush`，框选毫无反应**

```
BrushView._updateController
  → brushController.enableBrush(brushModel.brushOption)
                                ^^^^^^^^^^^^^^^^^^^^^^ 光写 option 时它一直是 {}
  → enableBrush 里 `brushOption.brushType && this._doEnableBrush(...)` 为假
  → 画笔永不启用：_brushType === undefined、面板没注册、mousedown 根本不处理
```

`brushModel.brushOption` 只在 `setAreas` / `setBrushOption` 里才被赋值
（`getInitialData` 里那一行在 ECharts 源码中是注释掉的），所以
`dispatchAction({type:'brush', areas: []})` 也没用（它遇到空数组直接 return）。
**官方示例一律走 `toolbox.feature.brush`，正是因为它会去 update 一次当前 brushOption。**

修法：拿 `getViewOfComponentModel(brushModel)._brushController`
再 `enableBrush({brushType:'rect', brushMode:'single', ...})`。

**② 一缩放，画笔就被关掉了**

同理：**dataZoom 一变，`BrushView` 就会重绘并再调一次
`enableBrush(brushModel.brushOption)`，而那里是 `{}` ——
`enableBrush({})` 会把已启用的画笔「停用」**（实测 `_brushType` 由 `rect` 变 `null`）。
所以"用户拖一下滑条或滚轮缩放之后，框选就再也不响应了"，而且看不出原因。

修法：在 `datazoom` 事件里**补一次** `syncBrushEnabled()`；
`applyRangeSelectMode` 自己派发的那个 dataZoom 动作也会触发它，顺序要对。

**③ 选框的背景色挡住 K 线**

`brushStyle` 走的是 **zrender 的样式键**（`fill` / `stroke` / `lineWidth`），
不是 canvas 那套 `color` / `borderColor`。**写错了不报错、也不生效**，
选框就一直用 ECharts 的默认浅灰填充盖在图上。实测对照：

| brushStyle | 实际生效的样式 |
|---|---|
| `{color, borderColor}` | `{lineWidth:2, stroke:'rgba(234,237,245,0.5)', fill:'#cfd2d7'}` ← 默认灰，挡图 |
| `{stroke, fill}` | `{lineWidth:1.5, stroke:'#3b82f6', fill:'rgba(59,130,246,0.08)'}` |

**④ 按不存在的字段做判断，把每一次框选都拒掉了**

`options.brush` 写对了、画笔也启用了、拖拽确实有反应 —— 但统计面板**永远不出现**，
而且"双击清除之后再框"也一样没反应。原因是组件里做过一个"框有没有落在图上"的
判断，用的是 `area.y` / `area.height`：

```js
// area 的**真实结构**（真 Chromium 抓下来的）
{ brushType, panelId,
  range:      [[206, 342], [150, 280]],       // 像素
  coordRange: [[10, 20], [157.79, 187.26]],   // 轴数据坐标 ← 要的就是它
  coordRanges, __rangeOffset }
// ⚠ 没有 x / y / width / height
```

`area.y` 与 `area.height` 都是 `undefined`，`Math.min(NaN, ...) > Math.max(NaN, ...)`
恒为 `false`，于是 `rangeFromBrushArea` 对**每一次**框选都返回 `null`。
表面上像是"框选功能坏了 / 清除之后坏了"，其实是同一个 `NaN`。

修法：换算只认 `coordRange`，把那段 y 判断整个删掉。
面板与时间轴一一对应，从成交量面板里框一段本来就该得到那段时间的 K 线统计，
不需要按面板过滤。

**⑤ `coordRange` 的形状是 `[[x0, x1], [y0, y1]]`，不是 `[[x0,y0],[x1,y1]]`**

这一条最阴：**它不报错，只是给出错区间**。按"两个点"的直觉去取
`[0][0]` 与 `[1][0]`，第二项拿到的是 **`y0`（y 轴上的价格）**：

```
目标：第 10~20 根   coordRange = [[10, 20], [157.79, 187.26]]
  正确取法 [0] = [10, 20]        → 区间 10~20   ✅
  错误取法 [0][0],[1][0]         → 区间 10~59   ❌（y0=157.79 越界后被夹到最后一根）
```

于是面板显示的涨跌幅是"从框选起点一路到数据末尾"，与框的时间段完全对不上。

**为什么第一次没发现**：早期那次实测的 `coordRange` 恰好是
`[[70, 92], [139.37, 187.26]]`，`[1][0] = 139.37` 与真正的 x1 很接近，
而 `Math.round(139.37)` 又越界被夹到最后一根 —— "看起来是对的"。
只有**先量出每个下标对应的像素位置、再精确地从第 i 根框到第 j 根、对比结果**，
才能暴露这种偏差。这也是补上后面那条"按已知下标精确框选"验证的由来。

**⑥ 顺带一个**：`chart.convertFromPixel({xAxisIndex: 0}, [px, px])` **返回 null**，
所以"自己把像素换成下标"这条路的终点也是 `NaN` —— 同样表现为统计不出现。

还有一条方向相反的坑：关闭框选时**必须显式 `enableBrush(false)`**。
只靠"下次 render 不再 enable"是关不掉的 —— 画笔一直留着，拖拽照样出框，
只是我们的统计面板不显示，又变成"拖了没反应"。

六条教训：

- `getOption().brush` 里有字段 ≠ 框选能用。**配置被接受**和**功能被启用**是两件事；
- **不要凭想象使用 ECharts 回调参数的字段名与形状**。`brushEnd` 的 `areas[i]`
  到底有哪些字段、`coordRange` 是"两对"还是"两个点"，只有在真浏览器里
  `JSON.stringify` 一次才知道 —— 用错不会报错，只会**静默地**让判断永远为假、
  或者给出一个看似合理的错数字；
- **"看起来对"不算验证**。数值类功能必须用**已知输入**做对拍：
  先 `convertToPixel` 量出每个下标的位置，再从第 i 根精确框到第 j 根，
  断言结果正好是 `[i, j]`；
- happy-dom 里 zrender 收不到 DOM 事件（它选了 pointer 通道而 happy-dom 不派发），
  所以这一整类问题在单测里既不能复现也不能排除 —— **交互必须用真浏览器验**；
- 回归用例要断言**行为**而不是配置：`tests/rangeSelectActivation.spec.ts`
  （13 个用例）用真浏览器抓到的 `areas[0]` 实测结构喂给 `brushEnd`，
  断言能算出 `{from: 10, to: 21}`（正好是框的那一段，不是一路到末尾）；
  另外还钉住开了会
  `enableBrush(rect/single)`、关了会 `enableBrush(false)`、datazoom 之后会再补一次、
  以及 `brushStyle` 用的是 `fill`/`stroke` 而不是 `color`/`borderColor`；
- 数值换算那一步单独抽成纯函数（`axisValuesFromCoordRange`），
  就能用实测值把它钉死。

> 真浏览器验证的做法（本次用的）：装 Playwright Chromium，
> 用 `page.setContent` 加载 CDN 版 ECharts 复刻组件 option 与事件处理，
> 再用 `page.mouse.down/move/up` 真拖。**六步都要过**：
> 框选后出统计 → 再框仍出 → 双击清除收起 → **清除后仍能框选** →
> 二次清除后仍能框选 → 关闭开关后拖拽不出区间。

统计全部在前端算，后端只记住开关（`showRangeSelect`）。
纯函数在 `lib/rangeStats.ts`，口径文案也在那里（`RANGE_METRIC_NOTES`），
所以**文案本身也被单测钉住** —— 那几句话是用户判断数字含义的唯一依据。

### 4. 条件选股（`/screener`）

左侧条件面板（基础面 / 行业概念板块 / 技术形态）+ 右侧结果表格。

条件逻辑移植自另一个项目 `tushare-stock-tonyz` 的 `StockSelector.filter_stocks`
（44 个参数）与 `apply_filter_post_filters`，按本项目的数据可得性做了裁剪。

#### 4.1 分层执行 —— 这是性能关键

```
快照层（0 成本：股票列表已在内存）
  → 板块层（0 成本：板块数据已缓存）
    → 技术层（要拉日线，只对前两层的幸存者执行）
```

如果技术层也对全市场执行，7500 只逐只拉日线要几分钟。实测：

| 场景 | 分层 | 耗时 |
|---|---|---|
| 市值>500亿 且 0<PE<20 | 7563 → 180 | 0.9s |
| 申万一级 = 医药生物 | 7345 → 457 | **28ms** |
| 医药生物 或 银行 | 7345 → 499 | **11ms** |
| 医药生物 且 概念创新药 | 7345 → 233 | 23ms |
| 医药生物 且 MA5>MA20>MA60 | 457 → 173 | 1.9s |
| 沪深主板 且 20日回撤 5~15% | 3039 → 1719 | 9.9s |

板块层只要十几毫秒，因为它复用同一份行情与板块缓存；只有技术层需要网络。

技术层用 48 个并发 worker 抓日线（`fetchWorkers`），每处理 200 只上报一次进度；
右侧顶部的进度条就是订阅后端的 `screen:progress` 事件画出来的 ——
否则几千只股票拉日线时界面会十几秒没反应。共享状态（命中列表、指标缓存、失败计数）
只在互斥锁内更新，**进度事件在临界区外发出**，避免持锁调用外部事件系统。

#### 4.2 条件清单

| 分组 | 条件 | 口径 |
|---|---|---|
| 规模 | 总市值 / 流通市值 / 成交额 | 界面单位**亿元**，后端换算 |
| 估值 | 市盈率(TTM) / 市净率 / **ROE** | ROE 由 `PB ÷ PE` 推导，仅当 PE 为正时有意义 |
| 交易 | 换手率 / 涨跌幅 / 量比 | %，涨跌幅可填负值（如 `-5 ~ -2`） |
| 开关 | 排除 ST、仅保留有行情、市场板块多选 | — |
| **板块** | **申万一级 / 二级 / 三级 / 概念**，多选 | 见 4.3 |
| 技术 | 均线比较（多条 AND）、阶段回撤 | 需拉日线 |

**字段缺失时跳过该条件**，而不是判为不满足 —— 否则会把「数据没同步」误判成
「不符合条件」，结果凭空少一批股票。这是原项目的行为，保持一致。

#### 4.3 板块/行业条件的数据源替换

原项目有四个数据源，本项目替换为 free-stockdb 已有的板块数据：

| 原项目 | 本项目 | 板块数 |
|---|---|---|
| 同花顺行业 `ths_industry` | **申万一级** | 28 |
| 同花顺行业（细分） | **申万二级 / 申万三级** | 104 / 227 |
| 同花顺概念 `ths_concept` / 东财概念 `em_concept` | **概念** | 978 |
| 东财行业 `em_industry` | 由申万三级覆盖 | — |

匹配语义**保持一致**：

- **条内「任一 / 全部」**：`any` = 属于选中板块的任一（并集）；`all` = 必须同时属于全部（交集）
- **多条条件之间是「且」**：例如「医药生物」且「创新药概念」求交集
  （原项目是不同数据源之间 OR，这里改成 AND —— 「行业 + 概念」求交才是常见诉求）

> 一条容易误解的地方：申万一级、二级、三级是**层级分类**，同一层级内互斥
> （一只股票只属于一个一级行业）。所以在同一分类下选两个板块并设 `all` 必然为空 ——
> 这是正确的，不是 bug。

**板块名写错会明确提示**，不会静默返回空结果：

```
以下板块没有找到，已忽略：概念 / 疫苗
```

（概念里的疫苗板块实际叫「生物疫苗」「HPV疫苗」，所以提示能帮用户改正。）

#### 4.4 数据湖条件（市销率 / 机构参与度 / 季报增长 / 相对强度）

这四项 free-stockdb 没有对应字段，**字段取自 cnequity 数据湖**。
「数据源完全不支持的条件」清单现在是**空的** —— 四个条件的字段都已经对接好了。

| 条件 | 数据集 | 字段 | 口径 |
|---|---|---|---|
| 市销率 PS | `valuation_metrics` | `ps_ttm` | 直接取 |
| 机构参与度 | `top_holders` | `is_institution` + `holding_pct` + `holder_scope` | 只算**流通股东**口径的机构，持股比例求和 |
| 季报增长 | `financial_statement_items` | `statement_type=income` + `item_code=net_profit` | 见下 |
| 相对强度 RS | `index_bars` | `close` | RS = 个股 N 日涨幅 − 对标指数 N 日涨幅 |

**字段已对接 ≠ 数据已入库**。这两件事对用户是不同的问题，所以界面上分开表达：
条件能正常用就标「可用」，否则标「等 `xxx` 入库」，并且**把数据集名字写出来** ——
用户才知道要去把哪个数据集跑出来。

数据集未入库时条件会被**跳过**（不报错、也不会静默生效），并在结果上方说明：

```
· 市销率条件已跳过：cnlake: valuation_metrics 尚未入库
```

**季报增长的算法**（数据湖的净利是**年内累计**值，单季要减上一季）：

```
单季(Q1) = 累计(Q1)
单季(Qn) = 累计(Qn) − 累计(Qn-1)
同比 = (本期单季 − 去年同期单季) / |去年同期单季| × 100
```

分母取**绝对值**：去年同期亏损时，增速的正负号才有意义。缺上一季、
去年同期为 0 或缺数据时判为「算不出来」而不是给出一个错误数字。

**RS 的对标指数**沿用原项目的映射，数据湖 `index_bars` 里这几个指数都有：

| 代码前缀 | 对标指数 |
|---|---|
| `300` / `301` | 399006.SZ 创业板指 |
| `688` / `689` | 000688.SH 科创 50 |
| `000` / `001` / `002` / `003` | 399001.SZ 深证成指 |
| `600` / `601` / `603` / `605` | 000001.SH 上证指数 |
| 其它 | 000300.SH 沪深 300 |

实测（`index_bars` 已入库，RS 可以真正跑通）：医药生物 20 日 RS 命中 338 只，
加 `RS > 10%` 后筛出 109 只；银行板块 40 只 → `RS > 5%` 的 7 只。

RS 需要逐只拉日线（和技术条件同一个窗口），所以启用后单次筛选要多花几秒。
指数当天没有数据时会向前找最近一个交易日。

#### 4.5 排序与结果

原项目的 `filter_stocks` **不做排序**（结果按代码升序），排序交给界面 —— 这里保持一致：
默认代码升序，点表头才按涨跌幅 / 市值 / PE / PB / ROE / 换手率 / RS 排序。
数据湖指标的列按需出现：数据集没入库时那些字段全是 0，显示一整列 0 只会让人困惑。

点击任意一行跳到该股的 K 线图表页。

#### 4.6 指定交易日

面板最上方可以指定交易日，**留空表示用最新交易日**。

指定日期时取的是**该日或之前最近一个有数据的交易日**，而不是那一天本身 ——
这个取舍是必须的：

- 用户填的那天可能**不是交易日**（周末、节假日）
- 更常见的是**当天数据还没同步**：收盘后到数据入库之间有窗口期，
  按"当天"取数会筛出半天甚至空的数据

实测（`20260930` 是最新交易日）：

| 指定 | 实际使用 | 说明 |
|---|---|---|
| 留空 | 20260930 | 最新 |
| 20260930 | 20260930 | 就是最新交易日，直接复用缓存，不再全量抓取 |
| 20261003（周六） | 20260930 | 回退，并给出提示 |
| 20261001（国庆） | 20260930 | 回退 |
| 20260928 | 20260928 | 精确命中 |
| 20260101（元旦） | 20251231 | 回退到上一个交易日 |

同一只股票在不同日期确实取到不同行情（`000001`）：

| 指定 | 收盘 | 市盈率 | 总市值 |
|---|---|---|---|
| 20260930 | 11.57 | 5.17 | 2245.3 亿 |
| 20260901 | 11.92 | 5.32 | 2313.2 亿 |
| 20260630 | 10.05 | 4.53 | 1950.3 亿 |

**三层都跟着日期走，只有板块层是例外**：

| 层 | 是否跟随指定日期 | 原因 |
|---|---|---|
| 快照层（市值/PE/PB/ROE/换手…） | ✅ | 按该交易日重建全量行情快照 |
| 技术层（均线/回撤） | ✅ | 日线窗口的**终点就是该交易日**，不会混入之后的数据 |
| **板块层（行业/概念）** | ❌ | **板块成分名单只有"当前"这一份**，数据源没有历史成分 |

板块层的限制是数据源决定的，不是实现偷懒 —— 所以指定历史日期且用到板块条件时，
界面会明确写出来：

> 板块成分名单只有当前这一份（数据源没有历史成分），所以板块条件按今天的成分股匹配，
> 只有行情类条件用的是 20260630 的数据

指定日期被回退时也会说明：

> 指定日期 20261003 不是交易日或当天数据尚未同步，已改用 20260930 及之前的数据

**几个实现要点**：

- 日期解析走 `Provider.TradeDateAt`（free-stockdb 用活跃股做探针走区间查询；
  数据湖读 `trading_calendar`），两边语义一致。
- 按日期的快照单独缓存（最多 4 个交易日），来回改日期不会反复全量抓取。
- 入参做**合法性校验**：`20260960`（9 月没有 60 号）、`20261301` 这类在入口就被挡下，
  提示按 `YYYYMMDD` 填写。不做这层校验的话错误会一路传到数据源，
  最后报一句"找不到该日期之前的交易日"，用户根本看不出是日期本身写错了。
- 界面用原生 `<input type="date">`，与后端的 `YYYYMMDD` 整数做一次转换。
- 提示文案是**纯文本渲染**的（带 `·` 前缀），所以后端不能往里塞 Markdown 标记 ——
  星号会原样显示出来。这一点有测试兜着。

#### 4.7 条件持久化

筛选条件在改动 500ms 后自动写入配置文件，下次打开接着用。
`GetScreenCondition` 用结构体而不是 Go 的多返回值 —— Wails 会把多返回值变成元组，
前端用起来别扭。

### 5. 财务 / 基本面数据

财务数据分三层，**能白拿的先拿到，拿不到的说清楚**。

#### 3.1 由行情推导：ROE 等 TTM 指标（已实现，零新依赖）

`日k` 里本来就带 `pe_ttm`、`pb`、`total_mv`，于是可以反推出 TTM 口径的财务指标：

```
ROE = EPS / BPS = (收盘价 / PE) ÷ (收盘价 / PB) = PB ÷ PE      ← 与股价无关
净利润(TTM) = 总市值 ÷ PE_TTM
净资产      = 总市值 ÷ PB
EPS = 收盘价 ÷ PE_TTM          BPS = 收盘价 ÷ PB
```

实测（2026-09-30，与本机 free-stockdb 对拍）：

| 股票 | 推导 ROE | 推导净资产 | 推导净利润 | 实际值 |
|---|---|---|---|---|
| 贵州茅台 | 32.40% | 2513 亿 | 814 亿 | ✓ 净利约 800–900 亿 |
| 工商银行 | 9.38% | 39879 亿 | 3740 亿 | ✓ 净利约 3600–3700 亿 |
| 平安银行 | 9.28% | 4678 亿 | 434 亿 | ✓ |
| 招商银行 | 13.27% | 11435 亿 | 1517 亿 | ✓ |
| 宁德时代 | 22.78% | 3731 亿 | 850 亿 | ✓ |

**优点**：全市场 7500 只、**逐日更新**、零额外数据源、离线可用。
**代价**：这是 TTM 快照，看不到营收 / 毛利率 / 资产负债 / 现金流等**科目明细**，也没有历史财报序列。
接口里通过 `FinanceSourceStatus` 明确标注每个指标的来源与口径，避免被当成财报读数误用。

#### 3.2 本地数据集已有

| 数据 | 来源表 | 说明 |
|---|---|---|
| 分红 / 股息率 / 复权因子 | `复权` | 每次除权的每股派息，可算股息率、近 12 月分红 |
| 资金流 | `资金流` | 主力 / 超大单 / 大单 / 中单 / 小单净流入，600519 有 1739 条（2019-08 起） |
| 股本 | `日k` | 总股本、流通股本 |
| 估值 | `日k` | 市盈率 TTM、市净率、总市值、流通市值 |

#### 3.3 cnequity 数据湖：两种角色

FreeStock 把数据湖当作**两用**资源，这也是「数据源」与「财务来源」的区别所在：

| 角色 | 何时生效 | 提供什么 |
|---|---|---|
| **财务数据来源** | **始终生效**（只要数据湖可达） | 财报科目、股本结构、股东户数、十大股东 |
| **行情数据源** | 在「数据源设置」里选中「本地数据湖」时 | 标的清单、日线、估值、资金流、分红、行业/概念板块 |

也就是说：**行情走 free-stockdb 时，财务数据照样从数据湖读**；反过来选中数据湖后，行情与财务都来自它。

#### 3.4 数据湖数据集 → 应用字段的映射

数据湖的 `daily_bars` **只有 OHLCV，没有 PE/PB/市值**（那些在 `valuation_metrics` 里），
所以行情需要组装，而不是简单换个读取器：

| 数据湖数据集 | 映射到 | 备注 |
|---|---|---|
| `instruments` | 标的清单、名称、资产类型 | `600519.SH` → 对外归一化成 `600519` |
| `daily_bars` | OHLCV | 按年分区 |
| `valuation_metrics` | PE_TTM / PB / 总市值 / 流通市值 | 按 `(symbol, trade_date)` 与日线关联 |
| `share_structure` | 总股本 / 流通股本 | 按变更日期取「截至该日生效」的值，用于算换手率 |
| `corporate_actions` | 分红送转 → 复权因子 + 每股派息 | 复权与股息率同一份数据，不能只取因子那部分 |
| `adj_factors` | 复权因子（备用） | 仅当 `corporate_actions` 为空时使用，因为它没有分红明细 |
| `fund_flow` | 资金流 | 字段名与 free-stockdb 不同，需映射 |
| `industry_members` | 行业板块 | `sw_l1` → 申万一级 |
| `sector_members` | 概念板块 | 归类为「概念」 |
| `trading_calendar` | 最新交易日 | 只取 `is_trading = true` |

`daily_bars` 只有 OHLCV 带来的连锁影响：昨收、涨跌幅、振幅、换手率**与量比**
都要在组装时算出来。

##### 量比必须自己推导

free-stockdb 的日K**自带 `vol_ratio` 列**，而数据湖的 `daily_bars` 没有 ——
所以这一项必须按定义算：

```
量比 = 当日成交量 ÷ 前 5 个交易日的平均成交量
```

三个刻意的口径决定（`internal/service/provider.go` 的 `volumeRatio`）：

| 决定 | 为什么 |
|---|---|
| 分母**不含当日** | 含进去等于把今天算进自己的基准，会**系统性压低**倍数（放量日尤其明显）。这是量比定义里最容易写错的一处 |
| 前 5 日**不足时返回 0**，界面显示「—」 | 次新股 / 长期停牌 / 刚入库的标的算不出量比。「—」是"算不出来"，与"量比 0 倍"是两件事 |
| 分母均量为 0 或当日成交量为 0 也返回 0 | 避免 `Inf` / `NaN` 流到界面 |

`volumeRatio` 是纯函数，三条取数路径（按股票缓存 / 全市场批量 / 区间）**共用**它，
所以不会出现"列表页和 K 线页量比不一样"。

> ⚠ 这里踩过一个坑：早先 `lakeProvider.buildQuote` **完全没填 `VolRatio`**，
> 于是"本地数据湖"模式下 K 线页的信息栏量比恒为空 —— 而换回 free-stockdb 就正常，
> 很容易被误判成"数据缺失"而不是"没算"。实测复核（600378 / 20261014）：
> 当日量 27,583,600、前 5 日均量 22,048,540 → 量比 **1.2510**，
> 且同一行的换手率 `volume/floatShare*100 = 2.5717%` 与接口给的 2.57% 自洽。

#### 3.5 性能：为什么需要批量接口

数据湖按年分区。股票列表要取 7500 只股票的最新行情，如果逐只查询，
**同一个年分区会被反复扫描 7500 次**。所以 `Provider` 接口里有一个批量方法
`LatestQuotes`：

- 数据湖实现：**一次读完分区**再按代码分组
- free-stockdb 实现：并发逐只查（它没有批量接口，但每次都是独立小请求，不存在重复扫描）

配合分区裁剪（按目录名里的年份前缀跳过无关分区）与列裁剪（类型化读取只取声明了的列），
单只股票取数只碰相关分区。

#### 3.6 数据位置与注意事项

FreeStock 内置只读读取器（`internal/cnlake`），位置按优先级：
环境变量 `FREESTOCK_CNLAKE` → 配置文件里的 `cnLakeRoot` → 「数据源设置」页的输入框 → 自动探测。

⚠️ **`cne init` 的坑**：如果 `phase2c_daily_bars_backfill` 失败，后续 phase 全部不会执行，
财报与行情都不会入库，日志里会出现
`still incomplete after retry (daily_bars); not starting later phases`。
设置页会把每个数据集「入库没有 / 多少行 / 哪些分区」列出来，一眼能看出卡在哪。

⚠️ **缺少 `daily_bars` 时不允许切换**：数据湖没有日线的话，切过去股票列表会是一片空白，
所以后端会拒绝切换并说明原因（财务数据不受影响，仍会继续从数据湖读）。

> free-stockdb 自己的在线财务接口（`get_fundamentals` / `set_init("host:12328")`）目前**不建议依赖**：
> 公共节点实测返回 502，且其实现位于闭源的 `stockdb.pyd` 里，协议无法从仓库源码还原。

设计要点：

- **配置放在程序目录**。路径按优先级解析：程序目录 → 用户配置目录（`%AppData%\FreeStock\`）。

- **自动迁移旧配置**。从旧版本升级时，如果程序目录还没有配置而 `%AppData%` 里有，

- **不再用浏览器 localStorage**。早期版本把指标设置存在 localStorage 里，

- **前端做防抖（400ms）**，避免拖均线周期时每次输入都写一次盘；关闭页面前会补一次落盘。
- **后端做 Sanitize**：手工改坏配置文件不该让界面崩掉 —— 非法周期回退到日线、
  慢线必须大于快线、颜色必须是 `#RRGGBB`、均线为空则回落到默认 5 条。
- **读配置先于取数**：复权方式存在配置里，读晚了会先用默认值多发一次请求。
- 界面上能看到它存在哪：K 线页的「指标设置」面板与设置页的「设置文件」卡片都会显示完整路径。

### 9. 组合管理（`/portfolio`）

逻辑移植自 `tushare-stock-tonyz` 的 `portfolio_service.py` / `portfolio_store.py` /
`portfolio_manager.py`。

> **当前是阶段一**：组合 + 持仓管理。策略轮动与回测是后续阶段，见第 10 节。

#### 9.1 存储：独立的 SQLite 库

组合、持仓、流水存在**单独的 `portfolio.db`**（与 `config.json` 同目录），
不塞进配置文件 —— 持仓流水会持续增长，配置文件不适合放这种数据。

驱动是 `modernc.org/sqlite`（**纯 Go，不需要 CGO**），代价是 exe 从 19.5 MB 涨到 23.5 MB。

组合库**按需打开**：首次用到组合功能时才建文件。这样即使安装目录只读
（装在 `Program Files` 下），也不会因为建不了库而让整个程序起不来。

三张表：

| 表 | 说明 |
|---|---|
| `portfolio` | 组合主表 |
| `portfolio_position` | 当前持仓，主键 `(portfolio_id, ts_code)` —— 一个组合一只股票只能有一条 |
| `portfolio_position_txn` | 持仓流水，**只增不改**，作为唯一审计账 |

原实现删组合时要手动级联清理 7 张表，漏一张就留垃圾；这里用外键
`ON DELETE CASCADE` 让它自己清干净。

#### 9.2 几条反直觉、但**如实照搬**的口径

这几条是移植时最容易"顺手改好"、结果与原实现不一致的地方，
所以代码注释和界面上都写明了：

| 口径 | 说明 |
|---|---|
| **数量是「层数」，不是股数** | 1 层 = 总资金的 `1/总层数`。整个组合模块**没有股数字段**，股数只存在于后续的回测引擎里 |
| **权重是「计划权重」** | `层数 ÷ 总层数 × 100`。股价翻倍后权重不会变，它不是市值权重 |
| **组合收益率不含现金** | `Σ(逐仓收益率 × 权重)`，是持仓收益的加权和，**不除以权重之和**。两个 10% 仓位一涨一跌 → 收益率正好 0 |
| **手动新增持仓时层数上限是 2** | 原实现 `min(2, max(1, ...))` 如此，尽管界面允许填到 999 |
| **取不到现价记 0** | 不是 NULL、也不报错，盈亏按 0 计。界面会单独提示有几只没取到 |
| **成本不含手续费** | 实盘成本口径；回测的成本才含费（阶段三） |
| **`rebalance_frequency` 是死字段** | 无论传什么，写入恒为 `signal`（条件触发）—— 原实现如此，如实保留 |

#### 9.3 两处有意的偏离

都是为了让代码更干净，**算出来的数值与原来完全一致**：

1. **`total_layers` 提升为组合级字段**。原实现把它放在一个全局的
   `data/portfolio_config.json` 里（默认 10），每次算权重都去读那个文件 ——
   于是"每个组合的仓位分母"实际上是个隐式的全局配置，多个组合无法用不同的分母。
   这里显式建模成组合字段。
2. **股票代码用 6 位裸码**（`600519`）。原实现用 `600519.SH`，而本项目其余部分
   （行情、K 线、板块、选股）统一用裸码，混用两套写法只会制造 bug。
   基准代码保留后缀（`000300.SH`），因为它是指数。

#### 9.4 现价从哪来

原实现从"最新评分日"的 `stock_strength_history.close_price` 取现价。
本项目阶段一还没有评分表，改为取**最新交易日的日 K 收盘价** ——
语义一致（都是最近一个有数据的交易日的收盘价），且复用股票列表的缓存，
不会为几只持仓单独发请求。

#### 9.5 数据库结构

```sql
portfolio(portfolio_id PK, name, portfolio_type, strategy_id, benchmark_code,
          status, max_stock_count, target_position_count, total_layers,
          rebalance_frequency, scope_type, scope_value_json, notes,
          created_at, updated_at)

portfolio_position(portfolio_id, ts_code, name, entry_price, entry_date,
                   position_layers, position_weight, source_type, holding_type,
                   strategy_tag, last_action, created_at, updated_at,
                   PRIMARY KEY (portfolio_id, ts_code),
                   FOREIGN KEY (portfolio_id) REFERENCES portfolio ON DELETE CASCADE)

portfolio_position_txn(txn_id PK, portfolio_id, ts_code, name, trade_date,
                       action, price, layers_delta, weight_delta, reason,
                       source_signal_id, created_at,
                       FOREIGN KEY (portfolio_id) REFERENCES portfolio ON DELETE CASCADE)
```

日期统一是 `YYYYMMDD` 字符串（与原实现一致，不是 DATE 类型）。

#### 9.6 每日调仓日报邮件

组合页顶部有一个**全局**的邮件订阅卡片（一套 SMTP、一套收件人、一个发送时间），
按点把当天每个活跃组合的调仓信息渲染成 **HTML** 邮件发出去。

界面上能看到的东西：启用开关、发送范围、SMTP 参数、收件人、发送时间与发送日、
邮件内容开关、**下次发送时间**、**上次发送结果与失败原因**、预览、测试发送、立即发送。

**发送内容**（每个组合一段，多个组合依次排列）：

| 区块 | 字段 |
|---|---|
| 邮件头 | 评分日、市场状态、生成时间 |
| 组合汇总 | 收益率、健康度与组合评分、持仓数、层数、仓位、最大回撤、现价口径 |
| **调仓动作** | 动作标签、代码、名称、评分、分差、候选、层数变化、原因 |
| 当前持仓 | 代码、名称、层数、权重、成本、现价、浮动盈亏、建仓日 |
| 候选池 Top N | 代码、名称、行业、总分、现价、RS20、120 日回撤（默认关闭） |
| 页脚 | 口径说明（层数不是股数、收益率不含现金…）+ 免责声明 |

几条**刻意的产品决定**：

1. **动作表按"该先做什么"排序**：清仓 / 换出 → 减仓 → 换入 / 买入 / 加仓 → 继续持有。
   邮件当待办清单读，按代码或评分排会让人自己去挑重点。
2. **候选池默认不附**：它能让邮件长一倍，而"今天要做什么"由动作表回答。
3. **生成不了建议也照发**：某个组合的评分还没刷新时，那一段写明原因（黄底提示框）
   而不是静默跳过 —— 否则用户会以为"策略今天没动作"。
4. **取不到现价显示 `—` 而不是 `0.00%`**：停牌被渲染成"平盘"是错误信息。
   没有持仓时最大回撤也显示 `—`（空仓不是"回撤为零，很安全"）。
5. **红涨绿跌**，与界面同一套颜色语言；动作标签的底色也按语义分档。

**渲染上的硬约束**（邮件客户端比浏览器苛刻得多，都有单测钉着）：

| 约束 | 为什么 |
|---|---|
| **全部样式内联**，不用 `<style>` 选择器 | Gmail / Outlook 会剥掉 `<style>` 块，只有 `style` 属性可靠 |
| `<table>` 布局，不用 flex / grid | Outlook 的渲染引擎不支持 |
| 不用外部图片 | 默认被拦截，拦掉后版式会塌 |
| 同时给 `multipart/alternative` 的纯文本分部 | 只发 HTML 时纯文本模式会显示成一堆粘在一起的文字 |
| 中文主题与显示名做 RFC 2047 编码 | 不编码就是乱码 |
| 正文 Base64 + 点号转义 | 未转义的行首 `.` 会被服务器当成 DATA 结束符，**而报错完全看不出是这个原因** |

**SMTP 实现**（`internal/email/smtp.go`，只用标准库）：

不用 `net/smtp.SendMail`，因为它只支持"明文连接 + STARTTLS 升级"，
而**国内主流邮箱（QQ / 163 / 企业邮箱）的默认端口 465 是隐式 TLS**（连上就握手），
对它直接不可用。换第三方库要多一份依赖，而这个项目对依赖很克制，
所以自己走一遍会话：握手 → EHLO（失败退回 HELO）→ 可选 STARTTLS → AUTH → MAIL/RCPT/DATA。

三种加密方式都支持，界面可显式覆盖，默认按端口猜：

| 方式 | 端口 | 说明 |
|---|---|---|
| `SSL` | 465 | 隐式 TLS（连上就握手） |
| `STARTTLS` | 587 / 25 | 明文连接后升级。**用户显式选它而服务器不支持时报错，不静默降级** —— 降级会把授权码明文发出去 |
| `none` | — | 仅内网 relay |

认证优先用 `LOGIN`（QQ / 163 / Exchange 兼容性最好），不被接受再退回 `PLAIN`；
服务器**不广告 AUTH 时也照样尝试**（部分企业网关如此）。
认证失败的错误信息会明说"请确认填的是 SMTP 授权码而不是登录密码" ——
服务器只回一句 `535 Authentication failed`，不说这句话用户会去怀疑地址、端口、防火墙。

**收件人**支持多个，换行 / 逗号 / 分号 / 空白混写都能解析（从 Excel 或邮件客户端
粘出来常常是混的），大小写不敏感去重。**非法地址不会被静默丢掉**，
而是原样列在界面上并在保存时拒绝。

#### 9.6.1 发送前先刷新评分

**这是这个功能能不能用的前提**，所以单独一节。

调仓建议是拿**某一帧评分**算出来的（`BuildPlan` 取 `MAX(trade_date)` 那一帧）。
那一帧如果还停在昨天 —— 应用刚启动、或当天盘后还没点过「刷新评分」——
算出来的建议就是基于旧数据的。发出去的就是一封**准时但过期**的邮件：
内容看着一切正常，数字却是旧的，**而收件人完全看不出来**。

所以发送流程是：

```
挑组合 → （默认）先把评分刷到最新 → 拿新评分生成建议 → 渲染 → 投递
              ↑ 顺序不能反
```

顺序反了（先拼内容再刷）等于"刷了却没用上"，正是要避免的事。
代码上由 `prepareDigest` 保证：**先 `refreshScoresBeforeSend`，再 `buildDigestFor`**。

| 决定 | 为什么 |
|---|---|
| **默认开启** | 不刷的话"准时发出的一封过期邮件"比"晚几十秒的正确邮件"更有害 |
| **只刷这封邮件用到的策略**（去重） | 刷一堆不会出现在邮件里的策略只是白花时间；多个组合共用一个策略也只刷一次 |
| **走增量**（`force=false`） | 评分只取决于 (代码, 交易日, 策略)，当天已算过的**一次行情都不拉**（见 `RefreshStrength`）。所以"盘后已经刷过"时几乎零成本，只返回一句 `SkippedFromCache` |
| **默认全市场**（`scoreLimit=0`） | 广度闸门按全市场统计「评分≥70 的只数」。只评一部分会让它被系统性低估、判成"广度不足"并删光买入信号 —— 那邮件里的建议就全空了。想省那几十秒的用户可以调小 |
| **失败不中止发送** | 数据源没起来时刷新会失败。这时"照发 + 在邮件末尾写明原因"比"什么都不发"有用得多 —— 用户至少知道策略今天没更新 |
| **刷新结果写进邮件** | 成功写「已刷新评分：N 个策略（全部标的），耗时 1.2s」，失败写「评分刷新失败（趋势成长）：… —— 该策略的建议可能基于旧评分」。**收件人能看到这封邮件的数据新鲜度** |
| **预览也走同一条路径** | 否则预览显示的是上一帧评分的建议、真正发出去的是刷过之后的 —— 两者对不上，"所见即所得"就没了。代价是点预览可能等几十秒（首刷） |

⚠ **一句必须说清楚的代价**：默认全市场首刷要几十秒（本机实测一次日更后约 30 秒，
之后当天再发都是秒回）。所以界面上把这一点写在开关旁边，并允许关掉；
关掉时界面明确警告"邮件会用数据库里现有的评分，建议可能基于旧数据"。

⚠ **调度器的重入保护**：因为"发送"现在可能持续几十秒，**比 30 秒的轮询间隔长**，
所以调度器里有一道闸门（`emailScheduler.begin()`）：拿不到就直接返回。
没有它的话第二次轮询会在上一次还没发完时又进来 —— **刷两遍、发两封**。
闸门必须 `defer` 放行，否则会永久关闭（"发过一次之后就再也不发"，且不报错）。

**定时发送**（`internal/service/email.go`）：

- 由**应用内的 Go 调度器**执行：每 30 秒醒一次判断"到点了吗"。
  所以**应用没运行时不会发送，也不会补发** —— 界面上写明了这一点。
- 判定用**一段 2 分钟宽的窗口**而不是 `now == HH:MM`：轮询落在 `17:00:29`
  这类时刻时，严格相等整分钟只命中一次，那一次被跳过这一天就没了。
  窗口内重复命中由**当天去重键**（`20261013 17:00`）挡掉，所以不会发两遍。
- **失败的发送不写去重键** —— 否则配置修好之后当天再也不会重试。
- **正在发送时不重入**（`emailScheduler.begin()`）—— 因为发送前要刷评分，
  一轮可能持续几十秒，比 30 秒的轮询间隔长（见 9.6.1）。
- 发送日按星期勾选；**不勾任何一天 = 每天发**（与"勾了工作日"是两件不同的事，
  所以不能用默认值把空数组填回去）。只勾工作日时**法定节假日仍会发**，
  本程序没有交易日历判断。
- 默认**关闭**，且关闭时不启动后台协程。

**存储**：设置在 `config.json` 的 `emailPrefs` 里
（含 `refreshScoresBeforeSend` 与 `scoreLimit`）。

> ⚠ `scoreLimit = 0` 表示**全市场**，是**合法值**。项目的通用工具
> `clampInt` 会把 `0` 当成"没填"回落到默认值 —— 而这里的默认值恰好也是 0，
> 一旦套用它语义就反了（`0` 会被换成别的数）。所以 `Sanitize` 里单独处理：
> 只有**负数**才收敛到 0（有单测 `TestEmailScoreLimitZeroIsMeaningful` 钉着）。

> ⚠ **授权码是明文存的**，没有加密。这是有意的取舍：加密密钥只能放在同一台机器的
> 同一个目录，挡不住能读到该文件的人，却会让"备份 / 迁移配置"需要额外解释。
> 所以界面上**把这件事写出来**，而不是让用户以为它被加密了；同时建议使用邮箱的
> 「SMTP 授权码」而不是登录密码。
>
> 授权码**不回传给前端**（`EmailPrefsInfo` 只有 `passwordSet`）—— 回传等于让它出现在
> DOM 与开发者工具里。界面上输入框留空表示"不改"，要清空有单独的按钮。

**测试**：`internal/email/smtp_test.go` 起一个**进程内的假 SMTP 服务器**跑真会话
（不是 mock 掉 session —— 那测的就只剩"我调用了 mock"），覆盖：
完整会话、不认证、`PLAIN` / `LOGIN` 机制选择、不广告 AUTH、认证失败提示、
收件人被拒、显式 STARTTLS 不被支持时报错、`HELO` 回退、参数校验先于建连、
报文结构（主题编码 / 点号转义 / 头注入 / multipart）。渲染侧另有：
转义、无动作时的原因、生成失败照发、缺失价格显示 `—`、内联样式、红涨绿跌、动作排序。

发送前刷评分那一块（`internal/service/email_refresh_test.go`）用**记账用的假 refresher**
钉住"刷了哪几个策略、传了多大的 limit、force 是不是 false"：
去重、走增量、默认全市场、关掉开关就一次不刷、单策略失败不影响其它与发送、
全失败时明说"可能基于旧评分"、命中缓存也给说明、nil 也不 panic。
调度器的重入闸门另有并发用例（16 个协程只有一个能拿到）。

### 10. 市场温度（`/temperature`）

把**大盘指数的多周期走势 + 量能**压成一个 0~100 的读数，回答一个问题：
**当前的市场状态，在它自己的历史里算热还是冷？**

数据来源只有**本地数据湖**的 `index_bars`（free-stockdb 没有指数表）。
本机湖里是 8 个指数、`2023-10-09` 起共 728 个交易日：

| 指数 | 代码 | 分组 |
|---|---|---|
| 上证指数 | `000001.SH` | 大盘 |
| 深证成指 | `399001.SZ` | 大盘 |
| 创业板指 | `399006.SZ` | 成长 |
| 科创50 | `000688.SH` | 成长 |
| 沪深300 | `000300.SH` | 宽基 |
| 上证50 | `000016.SH` | 宽基 |
| 中证500 | `000905.SH` | 宽基 |
| 中证1000 | `000852.SH` | 宽基 |

> 湖里**没有**北证50（`899050.BJ`）与中证2000（`932000`），所以界面写「8 大指数」而不是
> 「9 大指数」。代码是"注册表 ∩ 湖里实有"，注册表之外、湖里新增的指数会被自动带上
> —— 哪天把北证50 同步进湖里，页面会自己出现第 9 个，不需要改代码。

#### 10.1 温度怎么算

四个分项，**每个都先在全部样本里取分位**（0~100），再加权：

| 分项 | 权重 | 口径 | 为什么这么定 |
|---|---|---|---|
| 趋势 | 40% | 所选周期各指数涨跌幅的**等权**平均 | 温度首先问"在涨还是在跌"；等权避免沪深300 一个指数决定读数 |
| 量能 | 25% | 所选周期日均成交额 ÷ 近一年日均成交额 | 量能确认趋势的成色（放量上涨 vs 缩量反弹） |
| 位置 | 20% | 点位相对**自身 250 日均线**的平均偏离 | 反映"离长期趋势有多远"，是风险维度 |
| 共识 | 15% | 所选周期上涨的指数占比 | 普涨还是少数拉动 |

```
综合分 = 0.40×趋势分 + 0.25×量能分 + 0.20×位置分 + 0.15×共识分
温度   = 综合分在【全部样本】中的分位（0~100）
```

**温度直接读成「比历史上 X% 的交易日更热」**。取分位这一步是有意的：
四个分位数平均之后分布是中间密两头稀，取分位才能把读数均匀铺在 0~100 上，
极值才有意义（否则永远在 40~60 之间晃）。

#### 10.2 为什么「位置」不用点数高低

用户明确要求：**不能简单地以点数高低判断当前属于什么水平，因为估值一直在变**。

指数长期向上，点数天然越来越高 —— 直接比"点位在历史区间里的位置"，
任何时点都会被判成高位。所以位置分比的是
「**点位相对自身 250 日均线的偏离**」在全部历史里的分位。

实测差距（`2026-10-09`）：

| 指数 | 点数在历史中的分位 | 去趋势后的位置分位 |
|---|---|---|
| 上证指数 | 65 | **1** |
| 创业板指 | 67 | **0** |
| 科创50 | 80 | **0** |
| 沪深300 | 63 | **0** |

点数都在 60~80 分位（"高位"），但相对自身长期趋势都在 0~1 分位（"长期趋势下方"）。
`TestPositionScoreIgnoresRawPointLevel` 就是钉住这个差异的用例。

#### 10.3 界面

| 区块 | 说明 |
|---|---|
| 工具栏 | 周期：当日（默认）/ 5日 / 10日 / 15日 / 30日 / 60日 / 自定义（1~250 个交易日） |
| 温度面板 | 读数 + 等级（冰点/偏冷/中性/偏热/过热）+ 温度条 + 结论文案 + **四个分项的得分与权重** + 分位样本 |
| 走势对比 | 8 大指数最近 `max(周期, 20)` 个交易日，**归一化到窗口首日 = 100**（比涨跌幅，不比点位） |
| 指数卡片 | 每个指数：最新点数、当日与所选周期涨跌、迷你走势、**位置分位条**、MA20/60/250 关系、趋势标签与趋势说明 |
| 口径说明 | 权重、分位含义、为什么不用点数高低、数据来源与样本区间 |

**趋势说明**（每个指数一段）用可核对的事实拼出来，而不是只给一个标签：

> 跌破 20 / 60 / 250 日均线；当日 +0.05%（历史分位 50%）；量能仅为近一年均量的 0.83 倍；
> 点位相对 250 日均线 −4.44%（2023-10-09 以来 1% 分位）；距 2026-05-13 的高点回撤 10.11%。

#### 10.4 性能与数据限制

- 指数历史一次全读（`index_bars` 整表 154 KB、5824 行）：**约 10 ms**；
  全部计算：**约 15 ms**（切周期只是内存重算，实测 3~6 ms）。
- 指数历史缓存 30 分钟（切换数据源立即作废）；**切周期不取数**。
- **分位样本 = 四个分项都有值的交易日**：本机指数历史 728 天，但最早那 249 天
  还没有 250 日均线与"近一年量能"，把缺失当 0 或 50 会凭空造出一批极冷/中性的日子、
  污染整条分位分布，所以温度只用剩下的 **479 天**（2024-10-18 起）做样本。
  界面上"比历史上 X% 的交易日更热"用的就是这个样本。
  这是"有史以来所有数据"在数据源里**口径统一**的可得范围；湖里补了更早的年份，样本自动变长。
- 价格是不复权收盘价；分位用**含当日**的全样本计算 —— 这是"描述当前状态"，
  不是回测信号，所以不做滚动窗口（页面上也写明）。
- 数据湖不可用 / `index_bars` 未入库时返回**可解释的空状态**（`Available=false` + 原因），
  界面给出"去数据源设置看看"的下一步，而不是显示一屏 0。

把「这家公司现在值不值得买」拆成**五个独立期限**（1 / 3 / 6 / 12 / 36 个月），
从估值、成长、质量、安全边际、风险收益匹配五个方面给分并排名。

方案与实施记录：[`docs/A股多期限性价比评估方案.md`](docs/A股多期限性价比评估方案.md)、
[`docs/A股多期限性价比评估开发计划.md`](docs/A股多期限性价比评估开发计划.md)。

#### 11.1 三个"不能做错"的口径

这一节是整块功能的正确性基础，任何一条写错都会让全部结论失真。

**① 复权：收益用后复权价，市值用不复权价。**

数据湖 `daily_bars` 是**不复权**行情。实测 002594 在 2025-07-29 因 1:3 送转
由 337.00 直接变成 111.42，不复权算出来的 MA250 仍是 ~310。所以：

| 用途 | 口径 |
|---|---|
| 收益 / 波动 / 回撤 / 区间涨幅 / 情景收益 | **后复权**（不复权价 × F(t)） |
| 市值 / PE / PB / PS | **不复权原始价 × 当期股本** |
| 成交量 / 成交额 | 始终原始 |

代码里用两个不同的方法名强制分开：`Bar.AdjustedClose()`（收益口径）与
`MarketCap(rawClose, shares)`（市值口径），结构体同时保留 `Close` 与 `AdjFactor`。
`TestMarketCapUsesRawCloseNotAdjusted` 断言市值不能用复权价。

**② 财务是年内累计口径，且 Q4 是全年值。**

实测 600519 归母净利润（亿元）：

```
2023Q1 207.95  2023Q2 359.80  2023Q3 528.76  2023Q4 747.34   ← Q4 = 全年
2025Q4 823.20 = 2025 全年；2025Q4 单季 = 823.20 − 646.27 = 176.93
```

所以 TTM 只需要两段，**不需要把 Q4 减成单季**：

```
TTM(报告期 P) = 上年全年 + 本年至今(P) − 去年同期(P)
```

这条公式不是推理出来的，是**对拍验证**的：用 3941 只标的比较自建 PE 与数据湖
`valuation_metrics` 里的供应商 `pe_ttm` —— 中位比值 **1.0000**，**99.87% 落在 3% 以内**。
把 Q4 当单季再累加会得到 2~3 倍的偏离。

另外：同一报告期可能有多条修订，必须按 `announce_date` 只保留最新一批
（相加会把利润算成两倍，PE 算成一半）。

**③ 历史估值是自己重建的，不是读现成的。**

数据湖的 `valuation_metrics` 在本机**只有 5 个交易日**，拿不出历史分位。所以：

```
历史市值 = 当期股本（按变更日生效）× 当日不复权收盘价
历史 PE  = 历史市值 ÷ 当时**已披露**的 TTM 归母净利润
```

"当时已披露"由 `announce_date` 门控（本机该列 100% 有值，所以门控是硬的，
不是近似）。重建的 PE/PB/PS 与供应商口径并列展示做交叉检查，界面标明口径。

#### 11.2 估值是"四层 + 交叉验证"

| 层 | 内容 | 关键限定 |
|---|---|---|
| ① 个股自身历史估值 | PE/PB/PS 的 3 年 / 5 年分位、区间、归因 | 分位只说明**在自身历史中的位置**，不构成合理价值；检测到结构性变化（估值中枢或 ROE 中枢移动、成长阶段切换）时自动下调分位权重 |
| ② 行业整体估值 | 加权（调和口径）、中位数、历史分位**三者分列** | 加权是"总市值 ÷ 总盈利"，**不是**成分 PE 的算术平均 |
| ③ 相对行业与同行 | 折溢价、行业内分位、同行可比筛选、四象限 | 同行按"市值倍数 + 负债率 + 成长档位"逐级放宽，并如实写出放宽到了哪一级 |
| ④ 成长调整后的合理价值 | 七类方法自动选用 + 三情景 + 反向 DCF | 不把高增长直接换成高估值；不把行业平均倍数套到所有公司 |

七类方法（PE / PB / PS / EV/EBITDA / DCF / PEG / PB-ROE / 周期调整）**按行业与公司特征自动选择**，
不适用时输出原因而不是硬算，例如：

> DCF：36 个月 期限不做 DCF：现金流折现依赖长期终值假设，用在 12 个月上会把长期结论硬套到短期

多方法结论冲突时**不取平均**，而是解释冲突并下调置信度：

> PE 给出 40.00 元（区间 36.00~44.00），PB 给出 10.00 元（区间 8.00~12.00），
> 两者区间完全不重叠且相差 28.00 元。按方案要求**不取平均**：结论以置信度下调的方式反映这个分歧。

**安全边际 ≠ 潜在收益**（方案明确要求分开展示）：

```
安全边际 = (基准合理价值 − 当前价格) ÷ 基准合理价值
潜在收益 = (乐观价值   − 当前价格) ÷ 当前价格
```

#### 11.3 五档期限为什么不会给出同一个分数

"分别独立计算，不允许简单复制同一个评分"是靠**三重机制**保证的，不是靠把代码写五遍：

| 机制 | 1 个月 | 3 个月 | 6 个月 | 12 个月 | 36 个月 |
|---|---|---|---|---|---|
| 向合理价值收敛比例 | 12% | 25% | 45% | 75% | 100% |
| 成长权重 | 4% | 8% | 14% | 19% | 24% |
| 增速衰减系数（质量 60 分档） | ×0.74 | ×0.74 | ×0.55 | ×0.50 | ×0.40 |
| 悲观/基准/乐观概率 | 30/45/25 | 30/45/25 | 28/47/25 | 25/50/25 | 25/50/25 |

`TestHorizonsAreNotCopies` 逐一断言五档的评分、目标价、收敛比例、期限波动都不相同，
且收敛比例与波动幅度随期限单调递增。

#### 11.4 评分与风险约束

九个维度：自身估值 / 行业估值环境 / 相对同行估值 / 成长能力 / 成长与盈利质量 /
资本回报效率 / 安全边际 / 预期收益与风险 / 数据质量与置信度。

**同一份信息只在一个维度计分**，这条是硬约束而不是约定：`ValidateFactors` 会拒绝
"同维度重复 Key"与"跨维度重复 Key"，`TestFactorsAreNotDoubleCounted` 构造重复因子
断言它**真的会报错**（例如方案点名禁止的"行业估值偏低既计入行业评分、又计入相对估值评分"）。

九类风险约束分三级处置：

| 级别 | 含义 | 例子 |
|---|---|---|
| 一般预警 | 只标注，不改评分 | 高增长但现金流差、价格未复权、部分科目缺失 |
| 限制评级 | 评级封顶，并说明上限 | 估值低但盈利持续恶化（封顶中性）、溢价无基本面支撑（封顶偏低） |
| 无法可靠评估 | 不出评级，单独列出、**不参与排名** | 数据置信度低于 40 分 |

**原始分与最终分分开保留**（`rawScore` / `finalScore`），风险约束不改写原始估值结果。
实测输出（150 只大市值标的）五档均分 47~51、极值约 73 —— 评级分界就是按这个分布定的
（照搬"80 分才算优秀"会让所有标的都落在"中性/偏低"两档，评级失去区分力）。

#### 11.5 指数用独立模型

**不是**成分股评分的加权平均，也**不是**只看加权 PE：

- 估值用调和加权（总市值 ÷ 总盈利），同时给中位数 —— 两者背离越大，说明指数越被少数成分主导；
- 结构维度：亏损成分权重、便宜成分权重、贵成分权重、前 10 大权重、最大行业权重；
- 安全边际含量：有安全边际的成分权重合计（指数层面的"便宜货含量"）；
- 维度含义与个股**不同**：行业估值环境 = 成分估值分布的均衡程度；
  相对估值 = 加权与中位数的背离度。

本机 `index_constituents` 只有 1 个快照，所以 8 个指数里只有 5 个有成分数据；
其余 3 个只给指数自身的走势类结论，并明确标注"无成分数据"。

#### 11.6.1 性能：全市场刷新 ≤ 10 秒

| 路径 | 耗时 |
|---|---|
| 默认（前 150 只，冷启动） | 7.0 秒（读派生快照 5.0s + 评估 2.0s） |
| **全市场（limit=0，4400+ 只）** | **6.7~8.3 秒** |
| 换评估范围（重算评分） | 0.1~0.3 秒 |
| 同范围重复评估 | 0.0002 秒 |
| **点开个股详情** | **10~80 毫秒**（数据集已在内存时；同一只再来 0 毫秒） |

靠五件事达成，都值得记下来：

1. **派生数据快照物化到磁盘**（`<lake>/valuation_cache/`，四张表按代码哈希分 8 片并行读写）。
   首次从数据湖原始分区构建后**后台异步写**，之后每次冷启动直接读它。
   失效判据里最关键的是**数据湖最新交易日**（读它只要 4ms，比读 703 万行便宜五个数量级）。
2. **全市场行业基准用"轻量画像"**：只需要市值/PE/PB/PS/净资产/负债率，
   **不需要 1400 个交易日的价格序列**。价格序列推迟到真正评估某只标的时才建。
   > 这里踩过一个坑：曾经按"评估范围"决定谁要建序列，于是选「全市场」时
   > 给全部 5381 只都建了一遍 —— 那一步 **73ms → 4063ms**。
3. **两遍评估 8 路并发** + **TTM 建 (年,季) 索引**（原先是线性扫描，被调用 220 万次）。
4. **时点视图只算一次**：`evaluateOneStock` 过去算两遍 `BuildAsOf`，全市场 5383 只上
   实测 7.8s → 11.7s。
5. **个股详情复用同一份数据集**。曾经写成"详情页不走缓存"，理由是"只看一只没必要缓存
   全市场数据"—— 但 `focus` 只影响统计口径，**读的数据完全一样**。
   于是每点一只股票都把 703 万行行情 + 652 万行财报重读一遍：
   > 实测点开一只 **19.2 秒**，其中"加载数据集" 19.2 秒、真正算这一只 71 毫秒、
   > 行业聚合 26 毫秒。也就是 99.5% 的时间花在"读一份刚才已经读过、而且一模一样的数据"上。

> 试过但**更慢**的路：把 5 个数据集改并发读 → 15.7 秒变 37 秒
> （`readTyped` 内部已是 32 路 CPU 密集解码，外面再套一层等于开到 100+ 并发抢核）；
> 快照压缩 zstd 换 snappy → 只快 0.1 秒而体积涨 44%（说明读快照的大头不是解压而是落位）。

**每天第一次**（数据湖更新后）仍需重读原始分区：15~20 秒。这是数据量的物理下限，
且**在后台完成、不阻塞本次评估**。

#### 11.6.2 排名表的交互

- **虚拟列表**：全市场一档有 4400+ 行 × 15 列，一次性渲染是六万多个 DOM 节点，
  滚动会卡。现在只渲染视口内的行（`useVirtualList`），表格固定列宽。
- **行业筛选**：一排可多选的行业按钮（按成分数降序），可叠加、可一键清除；
  行业身份用 `industryCode`（带体系前缀，如 `sw:480301`）而不是名称
  —— 本机申万那一路的"行业名"**就是代码**，名称还会重名。
- **搜索**：代码 / 名称 / 行业名 / **拼音全拼** / **拼音首字母**，
  与股票列表页、K 线页搜索框**同一套规则**（`600519`、`茅台`、`guizhou`、`gzmt`
  都能搜到；多音字列全部读音，`payh` 与 `payx` 都能搜到「平安银行」）。

#### 11.6.3 市场隐含预期：高增长行业里最该防的那件事

**行业处于高增长，不等于该行业的每只股票都有高性价比。** 价格可能已经把未来
多年的增长提前反映完了 —— 这时基本面很好，预期收益却未必好。

这一节是为此加的独立模块。它回答三个**必须分开**的问题：

| 问题 | 用什么回答 |
|---|---|
| 行业整体贵不贵 | 行业成长阶段 + 加权/中位 PE + 历史分位 + 结构性口径兜底 |
| 个股相对同行贵不贵 | 成长调整后的相对估值（溢价能否被成长、质量、资本回报解释） |
| **当前价格在要求公司做到什么** | **反向 DCF 反解 + 隐含持续时间 + 兑现概率** |

前两个层次本项目早已实现（并用加权 PE 而非算术平均、用质量加权的 `fairPE`
而非 PEG）。第三个层次是本轮新增的 —— 原来的实现是**循环论证**：
它把 `fairPE`（成长+质量 → 合理 PE）反解回去，于是"高 PE"必然推出
"高隐含成长"，提供不了安全边际之外的任何新信息。

现在用**真正的反向 DCF**：复用正向 DCF 的同一个两阶段模型，二分求出
"让模型价值等于当前市值的增速"。并额外给出三个量：

- **隐含持续时间**——当前市值比"按公司自身增速折现的价值"高出的部分，
  相当于多少年的自由现金流。这直接回应了"PEG 忽略增长持续时间"这个经典缺陷。
- **兑现概率**（高/中/低）——结合"隐含要求 vs 自身能力"的差距、成长持续性、
  盈利质量判断（刻意用"短板优先"而不是加权平均）。
- **落空跌幅**——若成长只按自身实际增速实现，合理价值相对现价差多少。

两个新风险码接入评级约束：`growth_expectation_too_high`（价格隐含的成长要求
高于公司自身能力）、`growth_duration_demanding`（当前价格依赖长期高成长兑现）。

实测（2026-10-14，市值前 150 只的 12 个月档，可反解 74 只）：

```
药明康德 | 隐含增速 33.5% 需持续 16.1 年 | 自身 4.9% | gap +28.6% | 兑现低 | 落空 -45.0% | over
紫金矿业 | 隐含增速 -16.3% 需持续 0.0 年 | 自身 8.9% | gap -25.2% | 兑现高 | 落空 +84.6% | under
福耀玻璃 | 隐含增速 16.3% 需持续 0.0 年 | 自身 17.7% | gap -1.4% | 兑现高 | 落空 +3.0% | fair
```

药明康德那条正是这套机制存在的意义：行业（CXO）确实高增长，但市场要求它
**未来 16 年维持 33.5% 的增速**，而它近 3 年实际只有 4.9% —— 价格已经把
"高增长"提前反映完了。

**三条护栏**（方案明确要求，避免"高增长自动加分"）：

- 行业高增长**不给个股加分**。行业维度只通过合理价值的环境修正与
  隐含预期的分母起作用。
- 个股 PE 高于行业**不直接扣分**；看溢价能否被成长、质量、资本回报解释。
- 个股 PE 低于行业**不直接加分**；折价但基本面弱时加分打对折（价值陷阱）。

**口径边界（界面必须写明）**："公司自身增速"用的是**历史增速代理**
（近 3 年营收 CAGR），不是市场一致预期 —— 本机没有可回填的分析师预期数据
（`analyst_consensus` 只有 5 天且 `snapshot_only`）。自由现金流为负或
现金流科目缺季时，**如实判"暂无法反解"**并给出原因，不退回旧的循环反解。

#### 11.7 已知的数据限制（如实降级，不假装满足）

| 方案要求 | 本机实况 | 处置 |
|---|---|---|
| 用现成的历史估值数据 | `valuation_metrics` 只有 5 天 | 自建重建，界面标明口径 |
| 历史行业归属避免前视偏差 | 已有申万 2020 起 82 个快照 | **已时点正确重建**（该日生效的成分与股本） |
| 指数成分及历史变动 | `index_constituents` 只有 1 个快照 | 5 个指数有当前成分，其余只给走势类结论 |
| 申万行业分类 | 本机是 `eastmoney` 体系 | 接口按体系无关设计，界面写明 |
| EV/EBITDA | 无"折旧摊销"科目 | 用营业利润近似，仅在高负债率时采用，近似口径写进依据 |
| 验收 9（历史可追溯） | 财务/行情可完全满足，行业归属受限 | **部分满足** |
| 验收 10（历史验证） | 行业归属受限 | **部分满足**，框架已就绪 |

关键设计决定：所有历史相关接口一律 `asOf` 参数化。数据湖补齐历史成分后，
结论自动升级为完全满足，**不需要改模型代码**。

## 六、如何新增一个功能

前端：

1. `frontend/src/views/` 下新建视图组件
2. `frontend/src/router/index.ts` 注册路由（`meta.title` / `meta.subtitle` 会自动显示在顶栏）
3. `frontend/src/config/menu.ts` 加一个菜单项

后端：

1. 在 `internal/service/` 的 `StockService` 上新增导出方法，返回 `(结果, error)`
2. 重新生成绑定：`wails3 generate bindings -clean=true -ts`
3. 前端从 `@/lib/backend` 调用（`lib/backend.ts` 里集中封装了绑定入口）

## 八、数据来源

数据全部来自 **free-stockdb** 的本地 HTTP 服务（`http://127.0.0.1:7899`），
不像远程行情接口那样受限于并发配额。接口响应的 Content-Type 是
`application/x-msgpack`，因此本项目在 Go 侧自带了一个 MessagePack 解码器。

用到的表：

| 表 | 用途 |
|---|---|
| `股票代码` | 全市场标的清单 |
| `日k` | 日线行情 + 估值字段（PE/PB/市值/股本），也是周/月/年聚合与均线指标的输入 |
| `复权` | 复权因子 + 每次分红的每股派息 → 前/后复权、股息率 |
| `资金流` | 主力 / 超大单 / 大单 / 中单 / 小单净流入 |
| `板块*` | 申万一级/二级/三级、概念板块成分 |

财报类数据（营收 / 毛利率 / 资产负债 / 现金流）不在 free-stockdb 里，
需要从 cnequity 数据湖读取，见「一、3.3 本地数据集没有的」和「数据源设置」页。

**指数行情**（`index_bars`）同样只在数据湖里 —— free-stockdb 没有指数表，
所以「市场温度」页与「K 线图表」页的指数搜索/绘图都只在数据湖模式下可用
（本机湖里是 8 个指数、2023-10-09 起）。

**「多期限性价比评估」页用的是数据湖的另一批数据集**（与上面这些表无关）：

| 数据集 | 用途 | 本机实况 / 限制 |
|---|---|---|
| `daily_bars` | 价格与成交额（**不复权**） | 2616 个按交易日分区，2016-01-04 ~ 2026-10-14 |
| `meta/adj_factors_cache` | 后复权因子阶梯 | 5821 个 `<code>_<ex>_hfq.parquet` |
| `financial_statement_items` | 成长 / 质量 / 盈利 / 现金流 / 资本回报 | 888 万行、2001Q1~2026Q3、5612 只；`announce_date` 100% 有值 |
| `share_structure` | 历史股本 → 历史市值 | 168521 行、2001~2026、5928 只；`change_date` 是**年份**不是 DATE |
| `corporate_actions` | 近 12 个月每股派息（股息率） | 只覆盖 2023~2026 |
| `industry_members` | 行业归属与行业聚合 | ⚠ **只有 5 个快照**（2026-10-08~14），历史归属无法时点正确重建；体系是 `eastmoney`（非申万） |
| `valuation_metrics` | 只在"对拍校验"时用 | ⚠ **只有 5 个交易日**，所以历史估值是自己重建的 |
| `index_constituents` | 指数成分与权重 | ⚠ **只有 1 个快照**，仅 5 个指数有成分 |
| `index_bars` | 指数评估 | 8 个指数、2021 起 |

接口细节（请求格式、键表达式、表结构、性能实测）见
[`docs/free-stockdb-api.md`](docs/free-stockdb-api.md)。

> ⚠️ 请遵守 free-stockdb 项目自身的许可证与数据源条款。本项目只做数据读取与展示，不构成任何投资建议。

## 九、已知限制

- WebView2 需要一个可写的用户数据目录，否则窗口根本创建不出来。本项目已显式指定，
  详见第十一章排错。
- 首次加载需要向本机服务发起约 7500 次点查询（实测约 1 秒）；数据源换成远程节点会明显变慢。
- 概念板块允许一只股票属于多个板块，因此「按行业分组」视图中同一只股票可能出现在多个分组里。
- **没有财务报表**：本地数据集不含财报科目，ROE 等指标是由 PE/PB 推导的 TTM 快照，
  不是财报读数。补充方案见「一、3. 财务 / 基本面数据」。
  （「多期限性价比」页不受这条限制 —— 它直接读数据湖的财报科目。）
- **指数行情只有数据湖有**：free-stockdb 没有指数表，`index_bars` 里本机只有 8 个指数
  （无北证50 / 中证2000）、历史从 2023-10-09 起 —— 所以市场温度页是「8 大指数」，
  且分位样本只有约 3 年。湖里补进新指数或更早年份后，页面会自动跟着变。
- **多期限性价比评估的数据限制**（详见「一、11.7」）：历史估值是自己重建的、
  行业历史归属无法时点正确重建、指数成分只有 1 个快照、EV/EBITDA 缺折旧摊销科目。
  前两项让方案里"历史评估可追溯"与"历史验证"两条验收标准只能**部分满足**，
  且已在界面与置信度里如实标注。所有历史相关接口都是 `asOf` 参数化的，
  数据湖补齐后会自动升级为完全满足，不需要改模型代码。
- 多期限性价比评估的**全市场首刷要几十秒**（读 1400+ 个日分区 + 888 万行财报），
  所以默认只评估市值前 150 只；结果缓存 30 分钟，数据更新与切换数据源会主动作废。

## 十、排错

### 窗口一闪而过 / 完全没有界面

**最常见原因：WebView2 的用户数据目录不可写。**

Wails 的 `WebviewUserDataPath` 默认是空的，这时 WebView2 会把用户数据放进
`%APPDATA%\<exe 名>\`。该目录不可写（权限、安全软件、漫游配置异常，或被其它 WebView2
程序占用）时，`CreateCoreWebView2Controller` 会失败并返回 `0x800700AA`（ERROR_BUSY），
表现就是：

- 双击 `freeStock.exe` —— 没有任何窗口，任务管理器里进程一闪就没了
- 用控制台版排查时 —— 黑框一闪而过（见本章第 2 步）

**本项目已经修掉了这个问题**：`main.go` 里的 `webviewDataPath()` 会显式挑选一个
**确认可写**的目录（会真的写一个探针文件验证），按优先级：

1. `%LOCALAPPDATA%\FreeStock\webview2`
2. 写不进去时退回程序目录 `bin\webview2-data`

启动日志第一行会写明实际用了哪个：

```
[FreeStock] 启动，日志文件: ...\bin\freeStock.log
[FreeStock] WebView2 用户数据目录: ...\bin\webview2-data
[WebView2] Environment created successfully
```

如果你自己改代码后窗口又起不来，先看这两行目录是否正常。

### 界面是空白 / 数据出不来

前端本身已经用**真实构建产物 + 真实 free-stockdb 数据**在无头 Chrome 里验证过：
侧边栏、市场分类、行业分组、平铺排序、分页、搜索全部正常，控制台零报错。
所以界面空白基本都是 **WebView2 没创建成功**（见上一节）。

**第 1 步：看日志文件**（正式版也写，启动第一行会写明路径）

- `%LOCALAPPDATA%\FreeStock\freeStock.log`
- 写不进去时退回 `bin\freeStock.log`

正常启动的日志长这样：

```
level=INFO msg="[WebView2] Environment created successfully"
level=INFO msg=开始读取全量股票列表 source=http://127.0.0.1:7899 refresh=false
level=INFO msg=股票列表就绪 total=7563 withQuote=7546 tradeDate=20260930 markets=7 elapsed=740ms
level=INFO msg=板块数据就绪 boards=1337
```

**只要出现 `股票列表就绪`，就证明前端已经跑起来并调通了后端**，
这时候如果还看不到界面，就只剩「窗口被别的窗口挡住 / 在屏幕外」这类问题。

**第 2 步：需要看实时输出时，临时编一个控制台版**

`bin\freeStock.exe` 是 GUI 程序（PE 子系统 = GUI），**任何时候都不会弹黑框**，
所以它自己不会打印任何东西，只能靠日志文件。需要盯着实时输出时，临时编一个控制台版：

```powershell
go build -tags production -o bin\freeStock-console.exe .
.\bin\freeStock-console.exe
```

> 注意两点：
> 1. 不要用不带 tag 的 `go build`，那样走的是 Wails 的「开发模式」代码路径，和正式版行为不一致；
>    上面用的是 `-tags production`。
> 2. 这个控制台版是**临时排查用的**，平时不要拿它当程序入口 —— 它带黑框是正常的（PE 子系统 = 控制台）。
>    用完删掉即可：`Remove-Item bin\freeStock-console.exe`。

**第 3 步：F12**

窗口起来后按 F12 可以打开前端开发者工具（需要以 `-tags "production devtools"` 编译）。

### 其它

- `ERR_PNPM_IGNORED_BUILDS` → 见第四章的说明（`frontend/pnpm-workspace.yaml` 里的 `allowBuilds`）。
- 界面显示「数据读取失败」→ 说明前端正常、但连不上数据服务。确认 `stockdb.exe` 已启动，
  或在「数据源设置」里切换数据源。
